# PiPER 官方主从臂原生摇操操作说明

本仓库的 `piper_two_can_teleop` 现采用官方 `0xFA/0xFC` 固件直连方案。每侧一条 CAN：
主臂配置为示教输入臂 `0xFA`，从臂配置为运动输出臂 `0xFC`，两者使用默认偏移 `0`。
主臂直接发送 `0x151`、`0x155`～`0x157`、`0x159` 控制从臂。电脑只配置角色和观察
总线，不计算或转发运动目标。依据为[官方双臂说明](https://github.com/agilexrobotics/piper_sdk/blob/master/asserts/double_piper.MD)。

## 与已推送成功版本的区别

远端 `origin/humble` 的 `4c80c78`（“2can上位机摇操做初次尝试成功”）采用的是
`0xFC + 0x20` 上位机桥接：读取主臂 `0x2Cx` 反馈，由电脑向从臂发送
`0x151`、`0x155`～`0x157`、`0x159`。该版本使用官方 CAN 协议字段，
但不使用 `0xFA` 固件直连；其方案文档明确要求运行时不切换主臂为 `0xFA`。
因此这份原生联动实现不能视为对该成功版本的精简或复现。

软件已经切换到该方案；右主臂已按本文记录配置并在重启后核验，
其余臂的保存角色仍未完成核验。不能把监视程序启动
视为硬件角色已配置或联动已启用。`0xFA` 示教输入臂可能只发送控制帧，
单臂无反馈不能直接判定为 CAN 断线。
仓库最后一次已验证的左主臂配置仍是旧方案的 `0xFC + 0x20`；当前只读测试没有
发送角色配置，因此不能预期左主臂仅因运行本程序就进入 `0xFA` 重力补偿。

## 一次性角色配置

`0x470` 是广播帧，必须一次只接一台臂。另一台臂应断电或断开 CAN；命令中的
`--isolated-arm` 是操作员确认，软件只能核对单臂反馈，不能证明物理隔离。

先让目标臂单独连接到本侧 CAN，再执行：

```bash
source /opt/ros/humble/setup.bash
cd ~/piper_ros
colcon build --packages-up-to piper --symlink-install
source install/setup.bash

# 仅左主臂在线时
ros2 run piper piper_two_can_teleop --side left \
  --configure-role master --isolated-arm --send

# 仅左从臂在线时
ros2 run piper piper_two_can_teleop --side left \
  --configure-role follower --isolated-arm --send
```

右侧将 `left` 换成 `right`。程序先观察单臂反馈，随后要求输入
`CONFIGURE-MASTER` 或 `CONFIGURE-FOLLOWER`，才发送一次官方 `0x470`。
每台臂配置后断电重启。配置命令接受默认单臂反馈，也接受本仓库旧方案中
`0xFC + 0x20` 主臂的单臂反馈；偏移反馈只可转换为 `master` 角色。已处于 `0xFA`
且只发送联动控制帧的主臂无需重复配置。

## 上电与摇操

每侧先接通并上电从臂，再接通并上电主臂，等待固件联动输出。官方流程没有要求
再按一次实体示教按钮；`0xFA` 主臂上电后可能已处于可拖动状态。保持运动空间清空。
两侧可分别只读核验：

```bash
ros2 run piper piper_two_can_teleop --side left --port can_left
ros2 run piper piper_two_can_teleop --side right --port can_right
```

也可用 `ros2 launch piper start_two_can_teleop.launch.py` 同时启动两侧监视；接口名从
`config/pi05_can_map.json` 读取。监视窗口要求看见从臂完整反馈和主臂五类原生
控制帧各至少一帧，并拒绝旧偏移方案、额外控制帧、重复高速反馈及 CAN 错误帧。
未观察到完整签名前，程序逐窗口报告“未就绪”。确认过联动后若窗口内只有从臂反馈，
会明确提示该窗口未见主臂控制帧；单靠静止窗口不能区分主臂静止与输出中断。
若窗口内完全没有帧，程序只报告所见事实，不据此断言 CAN 接线故障。
收到 `0x471` 时显示载荷和数量；被动抓包不能断定它由哪台臂或哪个进程发送。
只有收到完整的官方帧签名，才能确认总线上出现了预期流量；这不能单凭抓包证明
从臂已实际运动或四台臂的角色已正确持久保存。

## 当前只读验证（2026-10-11）

使用新版监视程序同时观察两侧各 `3 s`：`can_left` 未收到任何帧；`can_right`
收到反馈，但缺少 `0x151`、`0x155`、`0x156`、`0x157`、`0x159`。
两侧均未达到官方原生联动的帧签名，原因尚未由只读数据确定。
观察前后内核 TX 计数保持 `can_left=0`、`can_right=9`，本次未发送 CAN 帧。
左侧零帧不单独证明接线故障；也不能把仓库历史上的角色配置当作当前角色读回。

右从臂断电并断开其 CAN 后，再次只读观察 `can_right`：连续 `5 s` 为零帧，
内核 RX 计数停止增长，TX 仍为 `9`。隔离前的约 `3040` 帧/秒因而与右从臂有关；
用户确认右主臂到 USB-CAN 的线路在拆接后仍然直通。隔离后零帧仍不能单独
断言右主臂的固件角色或控制器状态；下一步核对其当前供电并只读记录启动过程。

右主臂保持单独接入、绿灯且可拖动时，再次只读记录了它的断电重启。重启前为零帧；
上电后短暂出现 `0x171`（3 帧）、`0x175`～`0x177` 和 `0x179`（各 17 帧）、
`0x2C1`～`0x2C8`（各 1 帧），以及 `0x471 07 02`（3 帧）。随后流量停止。
电脑 TX 计数仍为 `9`，右从臂仍断开，因此这些帧来自右主臂。这与主臂保存了
`0x20` 控制/反馈偏移的情况吻合，且证明之前的重复使能至少有一部分由右主臂
自身发出；仅凭流量不能直接读回完整的 `0x470` 参数。官方零偏移直连要求主臂
发送 `0x151`、`0x155`～`0x157`、`0x159`，当前仍未满足。

程序增加了仅供旧偏移主臂使用的 `--recover-shifted-master` 路径：在目标主臂
单独接入时，先用至少 `20 s` 的只读窗口记录一次启动：要求 `0x171` 至少
`1` 帧，其余四类偏移控制帧各至少 `10` 帧；
抓齐后再观察 `2 s` 即提前结束，最长时间仅作等待上电的超时，
操作员确认后再用 `3 s` 窗口排除新接入的默认地址反馈、非目标控制帧、
非预期 `0x471` 载荷和 CAN 错误；目标主臂自己的偏移控制帧及
`0x471 07 02` 可以继续出现，
最后才允许发送一次 `0x470 FA 00 00 00 00 00 00 00`。该路径已通过离线测试。
如需对其他旧偏移主臂执行，目标主臂须受支撑且单独接入，另一台臂断电并断开 CAN：

```bash
ros2 run piper piper_two_can_teleop --side right --port can_right \
  --configure-role master --recover-shifted-master \
  --window-seconds 30 --isolated-arm --send
```

程序提示启动观察后，只重启右主臂；看到完整偏移启动帧才会要求输入
`CONFIGURE-MASTER`。若窗口内未见证据或最后的隔离检查不通过，程序拒绝发送。
发送后再重启右主臂，继续只读验证控制 ID 是否恢复为默认 `0x15x`。

首次现场尝试中，启动签名核验通过，但确认后的 `3 s` 窗口仍见目标主臂的
控制/使能流。旧门禁将它们也视为竞争控制而拒绝配置；内核 TX 保持 `9`，
没有发送 `0x470`。现已按隔离抓包证据收紧判别范围，如上所述。
第二次尝试的 `45 s` 启动窗口没有捕获到偏移控制帧，程序同样拒绝发送；
随后用户确认已重启，`can_right` RX 增加 `389` 帧而 TX 仍为 `9`，
说明这次重启流量晚于固定窗口。现已改为抓齐启动签名后提前结束，
并在下一轮开始前先确认操作员已准备好。

随后原始只读抓包再次记录右主臂单独上电：`0x171` 与 `0x471 07 02`
各 `1` 帧，`0x175`～`0x177`、`0x179` 各 `14` 帧，
`0x2C1`～`0x2C8` 各 `1` 帧，电脑 TX 仍为 `9`。因此将启动签名门槛按
实际帧数修正；旧门槛误要求只出现一次的 `0x171` 至少两次。
修正后右主臂单独重启时，程序通过启动签名和确认后的 `3 s` 隔离复查，
**实际发送一次** `0x470 FA 00 00 00 00 00 00 00`，进程正常退出。
内核 `can_right` TX 计数由 `9` 增为 `10`。
发送后的单臂断电重启只读抓包出现 `0x151` 一帧、
`0x155`～`0x157` 与 `0x159` 各 `14` 帧、`0x2A1`～`0x2A8`
各一帧，不再出现相应的 `0x17x` 和 `0x2Cx` 偏移帧。
这证明右主臂的零偏移角色配置在重启后生效；右从臂仍断电断 CAN，
完整主从联动尚需重新接入后的只读核验。

右从臂重新接入并先上电、右主臂后上电后，电脑只读抓包在约 `8 s` 内收到
`0x2A1`～`0x2A8` 各 `1600` 帧、`0x151` `50` 帧、
`0x155`～`0x157` 和 `0x159` 各 `255` 帧，未见旧偏移控制帧。
主臂控制帧按动作成段出现，有些观察窗口仅有从臂反馈。
用户当时报告右从臂随右主臂动作；这只能证明该次重新上电后曾发生联动，
不能据此认定此后持续运行。
接回初期监视窗口曾见短暂 CAN 错误帧，随后 `can_right` 保持
`ERROR-ACTIVE`，内核错误计数为零；仍应留意其是否复现。
本次 `can_right` 内核 TX 计数保持 `10`，联动时电脑没有转发运动帧。

随后用户指出右侧当前没有开始摇操作。现场再做 `8 s` 与 `45 s` 原始只读抓包：
后者共 `136788` 帧、`20` 个反馈 ID，`0x2A1` 为 `9000` 帧；
`0x151/155/156/157/159`、`0x171/175/176/177/179` 和 `0x471`
全部为 `0`。`can_right` 仍为 `UP / ERROR-ACTIVE`、`1 Mbit/s`，
内核累计 CAN 错误为 `0`。这只能说明该静止观察期没有主臂联动控制流，
当时尚不能判断动作时的联动状态。
随后用户澄清：右主臂一直上电、可重力补偿，稍后又能控制从臂，
但实体示教模式灯未亮。额外 `10 s` 与 `120 s` 只读记录仍只有约
`3040` 帧/秒的从臂反馈，均未见 `0x15x`、`0x17x` 或 `0x471`；
尚未确认用户是否在这两个记录窗口内实际移动主臂。因此不能把这些静止窗口
单独解释为联动故障，也不能仅凭实体示教灯判断官方联动是否工作。
需要将轻微主臂移动、从臂现场响应和同一时段原始 CAN 抓包对齐。

随后按“先准备、启动双接口原始抓包、明确通知轻微移动、用户立即回报”的顺序复核。
用户报告右从臂同步跟随；同一段抓包内 `can_right` 收到 `0x151` `52` 帧、
`0x155`～`0x157` 与 `0x159` 各 `97` 帧、`0x471` `52` 帧，
未收到旧偏移 `0x17x`。首条主臂控制帧后约 `76 ms`，从臂关节 1
的 `0x2A5` 反馈开始变化，本次范围 `1.316°`；其余关节保持不变。
`can_left` 全程 `0` 帧，`can_right` 内核 TX 仍为 `10`，
没有电脑转发运动帧。这次同步证据确认右侧固件直连在动作时实际工作；
静止期间主臂无控制帧不能单独判定故障。官方协议将 `0x06`
联动示教输入模式与 `0x02` 普通示教模式分开定义；实体示教模式灯未亮，
不作为本方案是否工作的判据。

右侧联动期间再次只读核对左侧：两臂据现场确认均已上电接线，但不跟随；
`can_left` 为 `UP / ERROR-ACTIVE`、`1 Mbit/s`，原始 `candump` 连续
`5 s` 为 `0` 帧，内核累计 RX/TX 仍为 `0/0`。
sysfs 与 udev 中 `can_left` 对应 USB 端口 `1-13:1.0` 和映射文件中的序列号，
`can_right` 对应 `1-4:1.0`。现有被动证据不能区分左侧控制器静默与物理接收路径问题，
也不能在左主从臂同时接入时广播 `0x470`；需要隔离后的交叉只读核验。
用户暂不拆接，因此左侧没有继续配置或发送任何 CAN 帧。
只读复核官方 SDK：`ConnectPort()` 默认会执行 `PiperInit()`，发出参数和版本查询，
不适合作为本阶段的被动测试。系统日志显示 `can_left` 已于当天 `14:50` 按
`1 Mbit/s` 配置并启用，之后仍为零帧；重复同样的接口重置不能提供关键区分证据。

随后用户让四臂断电，并在本机终端将 `can_left` 关闭、设为 `1 Mbit/s` 后重新开启。
接口恢复 `UP / ERROR-ACTIVE`，RX/TX 都为 `0`。左从臂单独上电后的原始抓包仍为
`0` 帧；左从臂断电、左主臂单独上电后，超过一分钟的原始抓包也为 `0` 帧，
均未收到启动反馈。

用户另行授权向仅左主臂上电的 `can_left` 发送一次官方参数查询：
`0x472 01 01 00 00 00 00 00 00`。这是关节 1 角度和最大速度查询，
不会使能、运动或写入配置。`cansend` 返回成功，发送队列记录 `1` 个包、无积压，
但 15 秒 `candump` 未见 `0x472` 本地回显或预期 `0x473` 回复；
内核成功 TX 和 RX 计数仍为 `0`，总线错误计数也为 `0`。
这只能证明帧被提交给适配器驱动，不能证明已经在 CAN 总线上完成发送。
左侧两台臂分别单独上电都没有自发帧；现有证据尚不能区分适配器、总线和设备端静默。
用户已将左主臂断电，授权对左侧 USB-CAN 适配器做软件级 USB 复位；
用户在本机终端执行 `sudo usbreset 001/008`。内核确认 USB 口 `1-13` 已复位，
同一序列号的适配器重新枚举为 `can_left`。用户重新设置 `1 Mbit/s` 并开启接口。
复位后仅左从臂上电，原始抓包仍为 `0` 帧，内核 RX/TX 仍为 `0/0`。
用户又单独授权对左从臂发送一次同样的 `0x472` 查询；包含错误帧的抓包
仍无任何帧，发送队列接收了 `1` 个包且无积压，但成功 TX/RX 仍为 `0/0`。
因此 USB 重新枚举及接口重建没有恢复通信；仍不能据此确认问题在适配器、
其 CAN 收发器、总线还是机械臂控制器端。

为进一步隔离适配器，用户让四臂断电并授权内部回环测试，保持 CAN 接线不动。
`can_left` 接受了 `loopback on` 配置，但执行 `ip link ... up` 时返回
`RTNETLINK answers: Protocol error`，内核报告
`usb 1-13: Error -71 while reading timestamp` 和
`gs_usb 1-13:1.0 can_left: failed to set bittiming: -EPROTO`。
因此回环模式并未启动，也没有发送测试帧。关闭回环、返回普通 `1 Mbit/s`
后再次启用仍报相同错误。随后用户执行 USB 软件复位，内核多次报告
`device descriptor read/64, error -71`、`Device not responding to setup address`，
左侧适配器从 USB 设备清单中消失，`can_left` 不再存在；
右侧适配器仍在，`can_right` 未受影响。这是发生在 USB 枚举和设置位速率阶段的
故障证据，比机械臂固件角色和 CAN 报文处理更早。当前不能继续左侧 CAN 测试，
需先恢复左侧 USB 适配器枚举。

用户仅重插左侧适配器的电脑端 USB 插头，未动 CAN 接线。内核在原口 `1-13`
重新识别相同序列号，`can_left` 重现；用户设为普通 `1 Mbit/s` 后成功启用。
随后仅给左从臂上电时，`can_left` 收到稳定的默认反馈 `0x251`～`0x256`、
`0x261`～`0x266`、`0x2A1`～`0x2A8`，RX 超过 6 万帧；因此左侧原先的
零帧问题至少包含 USB 适配器枚举/通信异常，重插 USB 后已恢复接收。
同一抓包内 `can_right` 也出现一套默认反馈，已请用户复核右侧实际供电状态。
左主臂的当前角色尚未在恢复后的接口上重新验证，不能据此宣称左侧联动已完成。

随后用户确认只有左主臂电源灯亮、左从臂及右侧两臂已断电。`can_left` 的单臂反馈
为旧偏移 `0x2C1`～`0x2C8`，并有 `0x251`～`0x256`、`0x261`～`0x266`，
未见默认状态 `0x2A1`～`0x2A8` 或联动控制帧。左主臂单独重启的抓包有约
`4.758 s` 空窗，重启后仍为旧偏移反馈；未观察到短暂的 `0x17x` 控制帧。
当前版本程序的稳态单臂预检查 `verify_isolated_arm(..., 'master')` 返回空问题列表，
其中 `0x2C1` 和 `0x2C8` 各有 `600` 帧/`3 s`、`0x2A1`、`0x470`、`0x471`
均为 `0`，CAN 错误帧 `0`。这与左主臂仍为旧 `0xFC + 0x20` 配置相符；
尚未写入新的 `0xFA` 配置。

未收到确认；该次记录为 `0` 帧。2026-10-13 用户确认左主从臂已按该顺序上电。
静止时 `can_left` 只有一套默认反馈，约 `3,000` 帧/秒，短窗口内未见主臂控制帧；
这不能单独判定联动故障。

同一段 `can_left` 抓包中，`0x151` 有 `26` 帧，`0x155/156/157/159`

主臂控制帧出现后，从臂关节 2～6 的 `0x2A5`～`0x2A7` 反馈发生变化，

`can_left` 内核成功 TX 仍为 `1`，仅对应此前授权的一次角色配置，
没有电脑转发运动帧。现场观察与总线证据共同确认左侧官方固件直连联动有效。
配置程序的 `17` 项定向测试通过，`py_compile` 与 `git diff --check` 通过；
本次同步复核只读，不发送 CAN 帧。

停止摇操应按设备的实体停机流程处理，并确认从臂状态。**Ctrl-C、关闭终端、
监视报错或关闭 ROS launch 都只停止电脑上的只读观察，不会停止固件联动或失能。**
本方案没有上位机姿态对齐、软件限幅、自动回位或 ROS 启停服务。若需要在联动结束后
单独控制从臂，须按官方说明先断开主臂的 CAN 连接，避免主臂继续发送目标覆盖电脑指令。
