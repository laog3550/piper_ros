## 修改结果

本次修复了《数据采集修改验收》中列出的三个优先问题和两个诊断、提示问题，并加载到现场只读采集进程。

- `start_collection.sh` 在加载 ROS 和工作区环境后启用 `nounset`；控制台明确使用 `/usr/bin/python3`，避免继承其他虚拟环境的 NumPy/OpenCV。干净终端可进入参数检查，真实启动入口可在隔离 ROS 域启动录制器、查询状态并正常退出。
- 录制中人工标记的完成帧保持原 Header。图像存在但来源或连续性不足时，保留标记并写入 `source_validation_error`；不产生替代该标记的尾部自动候选。引用图像不存在时保留事件及明确的图像核验失败状态，不授予完成帧资格。
- 原始保存写入独立的 `completion_validation` 帧门禁结果；顶层 `training_eligibility` 始终保持待独立验收，`eligible=false`。帧门禁通过不代表标定、来源验收、数据集划分和训练统计通过。正式转换器仍独立检查来源和训练契约。
- 完成帧校验失败抛出带结构化详情的 `CompletionValidationError`。候选记录片段号、片段总帧数、完成前有效帧数、窗口数及所需 16 帧；界面分别显示这些数量。无可用来源的失败不会伪造帧数或证明。
- CAN 诊断在同一统计锁内完成窗口快照和清零，保留间隙到达的更新供下一周期报告。

原有时间对齐、100 ms 时效、30 ms 同步和连续 16 步规则保持有效。没有补造原始 CAN、改写时间戳或将停发默认为保持。

## 增补的接收负载优化

第一次主动全负载复测中，右侧反馈在独立监听持续新鲜时出现连续 39 个 stale 采样点，内核 Header 到应用接收的峰值约 163 ms，队列无溢出。因此没有将第一次运行计为通过。

逐帧开销检查发现每条 CAN 都创建完整 SDK `PiperMessage`。现改为每个独立发布线程各持有一个 SDK 消息对象，在线程内复用；SDK 解析仍照常执行，输出字段与原始载荷仍逐条复制到新的 ROS 消息，不共用 ROS 消息或跨线程 SDK 状态。

固定输入、10000 次解码的本机微基准中，新建 SDK 消息约 0.515 秒，复用约 0.165 秒。这是解码微基准，不能推导整体吞吐或保证任意机器负载下实时性。新增用例对八类 CAN ID 混合的 1000 个输入，逐字段比较复用和新建对象的解码结果。
