## 结论与处理决定

验证提交为 `b6f752b1d089fe32abc1dd83f420d51ecf15d80d`，当前 `piper_direct_can_node.py` 的 SHA-256 为 `65172b6044602a226c4882ec6b737e54882717022d7e9ea010c9166c8cb9d2a2`，与该提交文件一致。

**本轮没有复现原始输入持续新鲜时的大量 stale。** 两次测试中左右反馈均无 stale；第二次实际操作主臂时，持续输入区间内的左右主目标也无 stale。按“先验证 P0；若仍大量 stale，再优先解耦接收与发布、之后优化 QoS”的顺序，本轮没有修改驱动线程结构或 QoS。

**P0 尚未全项通过。** 原始 CAN 的 bag 接收路径仍有延迟，且第二个诊断包末尾存在部分向量引用的原始 CAN 未入包。实时向量时效通过不能替代录制来源完整性验收。这些剩余问题尚未定位到 CAN 接收线程阻塞。

## 配置与方法

- 两侧只读直连 CAN、两侧向量节点、三路相机、桌面预览均保持运行；每个配置话题只有一个发布者。
- 三路相机为 640×480 RGB，约 15 fps；rosbag 使用 SQLite、256 MiB 缓存，原始 CAN/向量订阅 `KEEP_LAST depth=5000, RELIABLE`。
- 内核 `net.core.rmem_max=16777216`；直连 CAN 使用现有 16 MiB 接收缓冲请求。未修改内核配置、CAN 接口状态、源 Header 或质量标志。
- 独立 SocketCAN 监听器只读观察主目标 `0x155/0x156/0x157/0x159` 与反馈 `0x2A5/0x2A6/0x2A7/0x2A8`，与 ROS 向量的时效同时采样。
- 每轮先采空闲基线 5 秒，再进行 30 秒录制窗口，最后观测恢复 5 秒。稳态统计排除录制窗口前 3 秒。
- 第一次操作员未操作主臂，只作为静止反馈负载验证；第二次等待任一侧四类主目标 CAN 连续新鲜 1 秒后自动开始，实际由右侧触发，过程中两侧主目标都有输入。
- “瞬时原始输入新鲜”指独立 CAN 监听中同组四类 ID 的最老年龄不超过 50 ms；“持续输入”统计连续 6 个 50 Hz 观测点均满足该条件的区间，约 100 ms。向量 stale 门限始终保持 100 ms。
- 原始 bag 使用只读 SQLite 复核 Header、相机频率、原始 CAN 来源引用、接收时延及接口计数；两轮均无 SQLite 完整性错误、无图像 Header 倒退、无 CAN 接口 RX error/dropped 增量。

## 主目标总 stale 与恢复过渡

不排除停发区间时，第二轮 bag 中左主目标 `758/1387`、右主目标 `721/1386` 条 stale。独立 CAN 监听同时观察到源端目标帧中断，因此这些比例不能直接当作负载回压率。

预先设置的瞬时筛查条件是：原始四帧年龄不超过 50 ms 时，稳态 stale 比例超过 1%，或连续至少 5 个 stale 采样点，触发详细复核。左侧瞬时指标 `9/577=1.56%` 确实触发筛查；右侧为 `3/584=0.51%`。原始指标完整保留，未将它们改写为零。

逐事件检查这 12 次后发现：

- 全部恰好发生在此前源端停发、四类输入重新新鲜后的第一个观测点，`fresh_streak=1`。
- 上一个观测点的独立 CAN 最老年龄为约 82–1547 ms；个别事件还处于四帧组尚未全部更新的过渡。
- 下一向量周期全部恢复 `valid=true`，最长约 20.21 ms；未观察到连续多个“输入持续新鲜而向量 stale”的点。

这支持“停发后恢复时的单周期过渡”解释，未提供持续接收回压的证据。保持原始 stale 是必要的；线程解耦不能补出源端没有发送的目标帧。
