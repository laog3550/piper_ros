# 主从遥操作操作手册

本手册描述如何让一台 follower 臂跟随一台 master 臂。运动幅度与速度**由拖动 master
的人决定**，不由程序决定——这是与单关节测试最大的不同，也是风险主要来源。

> 本文档里所有 `ros2 run piper ...` / `ros2 launch piper ...` 命令都假定当前终端已经
> source 了 ROS 与本工作空间（`~/.bashrc` 只 source 了 ROS，**没有** source 本工作空间）：
>
> ```bash
> source /opt/ros/humble/setup.bash
> source ~/piper_ros/install/setup.bash
> ```
>
> 详见「完整 50 秒验证流程」第 0 步。

## 架构：为什么需要主机桥接

Piper 的固件级主从联动要求 master 臂在 CAN 总线上**直接发送**关节控制指令。但本
系统四台臂各自挂在独立接口上（`can_ml`/`can_mr`/`can_fl`/`can_fr`），master 发的帧
**不会**出现在 follower 的总线上。

因此遥操作由主机桥接：`piper_teleop` 读 master 的关节角度，计算 follower 目标，发到
follower 的指令话题。

```bash
# 1. master 侧节点（必须显式关掉 auto_enable，见下方陷阱）
ros2 launch piper start_single_piper.launch.py \
  can_port:=can_ml auto_enable:=false gripper_exist:=false

# 2. follower 侧节点
ros2 launch piper start_two_piper.launch.py \
  auto_enable:=false gripper_exist:=false

# 3. 使能 follower（master 保持失能，否则拖不动）
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: true}"

# 4. 先干跑看清对齐位移与回位计划，确认后再加 --enable
ros2 run piper piper_teleop --side left --duration 10
ros2 run piper piper_teleop --side left --enable
```

## 三个阶段

**对齐**：以 master 的**物理姿态为准**，follower 从自己的姿态移动到与 master 相同的
姿态。用三次插值（`3t²−2t³`）过渡，两端速度为零，所以起步和停止都没有速度突变。
**插值只用于这一个阶段**——两臂姿态本来就不同，正是需要平滑过渡的时候。

**跟随**：对齐完成后，follower 的目标就是 master 的**实时原值**，只经过两处处理：
越界钳制和默认开启的 α-β 状态估计（见下节）。目标值取自原值，但**能跑多快**另有限制
——见「跟随速度」一节（结论：瓶颈是 `--speed`，不是固件限速）。

**回位**：运行结束（`--duration` 到时或 Ctrl-C）后，follower 自动回到**启动时它自己
的姿态**（下称 home）。回位同样是三次插值，时长由位移和速度算出，不设固定时长。

实测左臂的对齐位移：j4 需移动 16.4°、j6 需移动 6.7°——**这不是微小幅度的动作**，
所以对齐必须平滑。速度由 `--align-seconds` 决定：**2026-09-23 把默认值从 8 秒改成
4 秒（2 倍速）**，位移 37° 时峰值约 14 deg/s，仍远低于实测跟随能力 86 deg/s。

对齐期间 **master 的姿态被冻结为轨迹终点**，而且程序一直在判断"操作者是不是已经
在拖它了"：

| 对齐结束时的情况 | 行为 |
| --- | --- |
| master 没被移动（偏差 ≤ 2°） | 进入跟随 |
| 被碰了一下**又停下**（偏差 > 2°） | 以新姿态重新对齐，最多 2 次 |
| **仍在被拖动**（> 1 deg/s） | 不再重新对齐，直接进入跟随 |

第三行是 2026-09-23 实测加上去的：操作者一直握着 master 拖时，对齐冻结的目标永远
追不上，重新对齐会把整个会话耗掉——那次 25 秒的会话里重新对齐 3 次，**最终模式仍然
是 align，follower 全程只在慢速追一个过时的快照，看起来就是"几乎不跟随"**。现在这种
情况直接进跟随，偏差由跟随自己收敛（滤波器用最后一次发布的目标做种子，命令流不跳）。

### 同步只允许保留 master 的原值

这是本工具的一条硬规则：**同步之后，任何对目标值的改动都会破坏两臂的关节同步**。
跟随阶段的目标链只有两处处理是保留的：

| 处理 | 跟随阶段是否启用 | 原因 |
| --- | --- | --- |
| 三次插值 | **不启用** | 只在两臂姿态不同（对齐阶段）时才有意义 |
| 越界钳制 | **启用** | 含越界目标的指令行为未定义，绝不能不处理 |
| α-β 状态估计 | **默认启用**（`--filter alpha-beta`，可切 `one-euro`/`lowpass`/`none`） | 同时估计平滑位置和速度，后者供平滑级做速度前馈；见下节 |
| 死区 | **默认启用**（`--deadband-deg 0.2`，0 关闭） | 小于阈值的变化完全不传递，手停着时目标一动不动；见下节 |
| 五次插值平滑 | **默认启用**（`--smooth-bandwidth 15`，0 关闭） | 固定带宽的三阶 jerk 受限环，压掉大幅度移动时的 5~15 Hz 抖动；见下节 |
| 跳变限制（`--max-step-deg`） | **默认关闭**（值为 0） | 它会削掉 master 的快速动作，让 follower 追不上 |

## 跟随阶段的处理链：死区 → One Euro → 五次插值平滑

### 为什么换掉一阶低通

原先用的是固定截止的一阶低通（τ = 0.02s，截止频率约 8 Hz）。**2026-09-23 实测发现
它压不住手抖**：手抖集中在 8~12 Hz，而 τ = 0.02s 在 10 Hz 处只衰减约 30%；把 `--speed`
提到 100 之后 follower 忠实复现了这段抖动，看起来就是"臂在抖"。

固定截止的滤波器有一个结构性矛盾：**要压 8~12 Hz 的手抖，截止频率就得压到 1 Hz 左右，
而在 30 deg/s 的拖动下那意味着 1.5 度以上的滞后**（滞后 ≈ 速度 / (2π·截止频率)）。
两者不可兼得，所以改用 **One Euro 滤波**（Casiez 等，CHI 2012）：截止频率跟着信号速度走。

### 算法

```
dx      = (x − x_prev) / dt                  # 原始速度
dx_hat  = 低通(dx, d_cutoff)                 # 速度本身先被低通
fc      = min_cutoff + beta · |dx_hat|       # 自适应截止频率
y       = 低通(x, fc)                        # 再用这个截止频率滤位置
```

`d_cutoff` 这一道是关键：**它挡住"手抖自己把截止频率顶开"**——若不滤速度，10 Hz、
±0.3 度的手抖会让 |dx| 达到 19 deg/s，把截止频率从 1 Hz 顶到近 4 Hz，反而把手抖放过去。

参数（默认值）：`min_cutoff = 1 Hz`（静止时）、`beta = 0.3 Hz per deg/s`（自适应强度）、
`d_cutoff = 1 Hz`（速度估计）、`dt` 用**实测**循环间隔。

### α-β 默认参数的理论推导

每个关节维护估计位置 `q` 与估计速度 `v`。周期 `dt` 内先按匀速模型预测，再用
master 实测角度 `z` 修正：

```text
q_pred = q + v·dt
r      = z - q_pred
q      = q_pred + α·r
v      = v + β·r/dt
```

忽略测量噪声时，位置误差 `e_q` 与按一个周期归一化后的速度误差 `dt·e_v` 的离散
状态矩阵为：

```text
A = [[1-α, 1-α],
     [ -β, 1-β]]
```

其特征多项式满足：

```text
trace(A) = 2 - α - β
det(A)   = 1 - α
```

为了不让两个误差模态一快一慢，默认把两个极点都放在 `λ=0.40`。令
`trace(A)=2λ`、`det(A)=λ²`，直接得到：

```text
α = 1 - λ²     = 1 - 0.40² = 0.84
β = (1 - λ)²  = 0.60²      = 0.36
```

两极点都严格位于单位圆内，所以无噪声下估计误差稳定收敛。50 Hz 时 `dt=0.02s`，
离散极点对应的连续时间常数为：

```text
τ = -dt / ln(λ) = -0.02 / ln(0.40) ≈ 0.0218s
```

单一模态经过约 `3τ≈0.065s` 衰减到约 5%；重复极点会带来额外的多项式项，因此真机
应以记录数据验证最终整定。

**λ 的选取有实测依据（2026-09-24 真机反馈「抖动已可接受、但迟滞明显」后重定）。**
匀速段的滞后与 α、β **无关**：速度估计收敛后前馈把稳态滞后补成 0（离线实测：任何
α-β 组合在 1~150 deg/s 的稳态滞后都是 0 度；对照组去掉前馈后 100 deg/s 滞后 11.3 度）。
这两个增益只影响**起步、变速与反向的暂态**，所以按实测表选：

| λ | α | β | 静止残留抖动 | 变速 20→100 | 反向 +60→−60 | 急停 100→0 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.65（原默认） | 0.5775 | 0.1225 | 0.021° | 5.12° | 9.48° | 8.90° |
| 0.50 | 0.75 | 0.25 | 0.039° | 3.96° | 7.73° | 7.45° |
| **0.40（当前默认）** | **0.84** | **0.36** | **0.052°** | **3.39°** | **6.89°** | **6.74°** |
| 0.30 | 0.91 | 0.49 | 0.071° | 3.01° | 6.31° | 6.26° |

（单位均为度；抖动为 10 Hz、±0.3 度手抖下输出的峰峰值，三列暂态为 100 deg/s 动作
下与 master 的峰值偏差，数据来自同一条流水线（死区→α-β→平滑级）的离线扫描。）

当前默认取 λ=0.40：暂态比原值降约 1/3，残留抖动 0.052° 仍在机械臂自身本底
（0.011~0.041°）量级；再快到 λ=0.30 只多降约 10%，抖动却上升四成。换暂态的是 **β**
（速度估计的收敛速度），α 只决定位置平滑程度——把 β 单独从 0.1225 提到 0.36 能得到
与 λ=0.40 几乎相同的收益，但抖动同样上升，所以仍按极点公式成对改，不要单独放大 β
去追响应。

`--alpha-beta-max-dt=0.1` 来自 50 Hz 标称周期的 5 倍：出现这么长的调度空洞时，
匀速模型已经不可信，程序会以最新测量重新锚定并把速度清零，不把旧速度外推过整段
空洞。

### 旧滤波方案数值对比（50 Hz，10 Hz、±0.3 度手抖模型）

| 方案 | 静止时残留抖动 | 10 deg/s 滞后 | 20 | 40 | 100 |
| --- | --- | --- | --- | --- | --- |
| 一阶低通 τ=0.02s（旧） | 0.146 度 | 0.20 | 0.40 | 0.80 | 2.00 |
| 一阶低通 τ=0.05s | 0.079 度 | 0.50 | 1.00 | 2.00 | 5.00 |
| One Euro（保留作对照） | **0.036 度** | **0.22** | **0.28** | **0.35** | **0.43** |

（单位除标注外均为度，数值来自 `test_piper_feedback.py` 中同一模型的离线计算。）

**两个方向都更好**：静止时的残留抖动比旧低通小 4 倍，快速拖动时的滞后小 4.7 倍。
这也解释了为什么旧方案"抖动还是很严重"——它的截止频率是给噪声选的，不是给手抖选的。

### 使用与调节

`--filter` 选方案：`alpha-beta`（默认）、`one-euro`、`lowpass`（旧的固定截止低通，留作对照）、
`none`（不滤波，同步优先）。

α-β 调参优先保持两个极点相等：选一个 `0<λ<1`，再用
`α=1-λ²`、`β=(1-λ)²` 计算（λ 越小越快、抖动越大，上节有实测的四档）。
留意：**它只改暂态**——匀速跟随的滞后在驱动器执行侧，调这两个值不会改善。
One Euro 对照方案的调参经验：

- 静止时还在抖 → 调小 `--one-euro-min-cutoff`（0.5 会更狠，代价是起停更"粘"）；
- 拖动时觉得跟不上 → 调大 `--one-euro-beta`（0.5 时 100 deg/s 的滞后降到 0.27 度）；
- 位置抖动被误当成运动、截止频率乱开 → 调小 `--one-euro-d-cutoff`（0.5 更稳）。

### 死区：让"停着的手"不再产生任何运动

One Euro 压的是快抖（5~15 Hz），但它的截止频率在静止时是 1 Hz——**1 Hz 以下的慢晃
它几乎原样放行**。手扶着重物时那种慢晃正是要消掉的东西，所以在滤波器前面再加一道
死区（`--deadband-deg`，默认 **0.2 度**）。

**它必须同时看幅度和速度**，只看幅度会有一个致命副作用（2026-09-23 真机暴露）：

| 死区策略 | 1 deg/s 慢拖时指令速度的表现 |
| --- | --- |
| 只按幅度（第一版） | 在 **0.18~1.60 deg/s** 之间反复起伏（std 0.42）：慢拖被切成 0.2 度一级的台阶，台阶之间速度归零、落下时又突然加速——操作者的原话是"每一小段速度都会归为零然后重新加速" |
| **幅度 + 速度门限（现行）** | **恒定 1.00 deg/s**（std 0.00）：只要在动就连续跟随 |

规则：**只有当输入既没有越过幅度阈值、速度又低于 `--deadband-speed`（默认 0.8 deg/s）
时才保持输出**；一旦在动，锚点跟着走、什么都不保持。速度是这一级自己估的（每周期
差值再过一道 3 Hz 低通），所以不依赖上游。

| 情形 | 行为 |
| --- | --- |
| 手停着（慢晃 ±0.15 度、速度约 0.3~0.5 deg/s） | **输出一动不动** |
| 慢拖（≥ 0.8 deg/s，含 1 deg/s 的精细定位） | 连续跟随，**速度不归零** |
| 快速拖动 | 死区完全不参与 |
| 5 Hz 以上的快抖 | 速度门限会放行（它"在动"）。压它靠的是整条链的频率响应，而且是**分频段**的：10 Hz 处残差约为输入的 1/12，5 Hz 处只压到一半（速度前馈在这个频段几乎是透明的，见「α-β 默认参数」一节）。所以死区管的是"停着不动"，快抖靠平滑级，两者不重叠 |

代价与边界：

- 速度估计需要约 0.05 秒（3 个周期）建立，所以**从静止起动的头 0.05 秒**仍按旧的
  幅度规则走，保持量小于 0.2 度；
- 前馈通路会漏回约 1/5 的手抖（One Euro 的速度估计在 1 Hz 处仍留 20% 的手抖导数）。
  整条链对 ±0.15 度 5 Hz 手抖的残留约 0.03 度，已在机械臂自身本底（0.011~0.041 度）
  量级，再压就要拿跟手性去换；
- 停下后目标最多停在离 master 真值 0.2 度的地方（幅度阈值，方向与刚才那次移动一致）。

### 五次插值平滑（jerk 受限级联环）

这一级解决的是**"大幅度移动时抖动严重"**：One Euro 的截止频率随速度线性打开
（100 deg/s 时约 31 Hz），手抖与结构振动都会跟过去。平滑级用一条**带宽固定**的三阶
级联环（位置→速度→加速度→jerk）把 5~15 Hz 整段压掉，同时用**速度前馈**（One Euro
内部那个滤波后的微分）保住跟手性。

```
每个关节维护 (位置, 速度, 加速度)，每周期走一步：
  期望速度 = k_p·(目标−位置) + 前馈速度        k_p = ω/2
  期望加速度 = k_v·(期望速度−速度)             k_v = ω
  jerk      = k_a·(期望加速度−加速度)          k_a = 2ω
  加速度 += jerk·dt → 速度 += 加速度·dt → 位置 += 速度·dt
```

增益来自**三阶 Butterworth 极点配置**（特征多项式 `s³+2ωs²+2ω²s+ω³`），所以只有
**一个**调参量：带宽 ω（默认 15 rad/s ≈ 2.4 Hz）。jerk 是最内层的指令，因此**加速度
连续、没有跳变**——这正是"五次插值"要买到的东西。

**真机数据的正确读法（2026-09-23 修正）**：三次 50 秒自由拖动的对比一度给出"滞后降
6~10 倍"的结论，那是**错的**——每次运行操作者拖的内容不同，而滞后随拖动速度增长，
直接比较是把"这次拖得慢"当成了"滤波器更好"。按**同一速度档**归一化后，三种配置的滞后
基本一致：

| 运行 | 1~5 deg/s | 5~20 | 20~80 | 80~400 |
| --- | --- | --- | --- | --- |
| 基准（无平滑级） | 1.007 | 2.600 | 7.893 | 28.495 |
| 平滑级（旧死区） | 1.004 | 2.047 | 7.046 | — |
| 平滑级 + 速度门限 | 1.367 | 2.685 | 7.905 | 21.703 |

（单位：度，同一拖动速度档内的滞后中位数。）所以**指令侧这一级对跟随滞后没有可测的
改善**，它的作用是把高频抖动压到机械臂自身本底；拖动的滞后主要由拖动速度和驱动器
执行决定。

静止段（master 连续静止 ≥1 秒）里 follower 的 5~15 Hz 抖动是唯一能干净对比的场景：
0.0106（基准）/ 0.0079（旧死区）/ 0.0241（速度门限）度——都在机械臂自身本底
（0.011~0.041 度）之内。**速度门限让静止时略"活"一点**（它会把速度超过 0.8 deg/s 的
成分放行），这是为了换"慢拖不被切成台阶"，是有意的取舍；想更静止就调小
`--deadband-speed`。

**离线（真实拖动数据，50 Hz）**：

| 项目 | 结果 |
| --- | --- |
| 5~15 Hz 抖动衰减 | **95~98%**（j1/j4/j6 实测；合成 ±0.3 度 10 Hz 叠 100 deg/s 拖动衰减 98.8%） |
| 跟随滞后中位 | **0.00~0.24 度**（不加这一级时是 1.5 度） |
| 阶跃过冲 | 约 1.8%（30 度阶跃 0.55 度） |
| 急停过冲 | 150 deg/s 急停时约 **7.6 度**（这是代价：制动距离 ≈ 速度/带宽） |
| 硬上限 | 速度/加速度/jerk 三个上限是安全网，正常由 ω 决定形状；速度上限可能被超出千分之几 |

**为什么不是"每周期重规划一条五次多项式"**：那个方案我做过三个原型，都在数值上失败
了——静止到静止的规划让匀速拖动时的稳态滞后发散（100 deg/s 时 59 度、150 deg/s 时
389 度，数学上滞后 = 5.77·v²/a），加"可停速度上限"后急停/反向会冲过目标 66~86 度，
加目标速度前馈后每周期只走到规划曲线最平缓的开头、速度永远起不来（150 deg/s 的目标
只跑到 53）。根因是两条：加速度受限必然限制"速度能多快改变"，而逐周期重规划会反复
采样曲线的起始平坦段。级联环没有这两个毛病，因此选它作为正式实现。

调参：`--smooth-bandwidth` 越大越跟手、急停过冲越大（20 rad/s → 过冲约 5 度）；
越小越平滑、滞后越大。0 表示关掉这一级。三个上限一般不用动。

### 两条不变的约束

- **只作用于跟随阶段的 master 读数。** 对齐与回位是规划好的三次插值轨迹，不滤波。
- **进入跟随的那一刻用当前 master 值初始化滤波器**，否则滤波输出会从 0 开始爬升，
  那本身就是一个真实的起始跳变。**种子取的是最后一次发布的目标**，不是 master 的
  当前值——这样即使对齐期间 master 被拖走很远，命令流也是连续的，偏差由滤波输出
  自己收敛过去。

以及一条与滤波无关的事实：**滤波只平滑形状，不限制幅度**。速度上限由 `--speed`
与机械能力决定（见「跟随速度」一节），滤波器不参与限速。

## 结束回位

home 就是**本程序启动时 follower 的姿态**，自动记录，没有配置参数。

| 项目 | 行为 |
| --- | --- |
| 触发 | `--duration` 到时、Ctrl-C（`--no-return-home` 可完全关掉） |
| 起点 | 最后一次发布的跟随目标（命令流连续）；干跑时 follower 不动，用它预览真实运行的计划 |
| 时长 | 由位移和速度算出，**不设固定时长** |
| 曲线 | 三次插值 `3u²−2u³`，两端速度为零 |
| 读 master | **不读**，回位是独立动作 |
| 使能校验 | 回位前、回位中每周期都校验整臂 ENABLED |
| 第二个 Ctrl-C | 立即中止回位，机械臂停在原地 |

时长公式：`Δmax = max|home − 起点|`，然后

```
T = max( Δmax / --return-speed , 1.5 × Δmax / --return-max-peak )
u = t / T      s = 3u² − 2u³      目标 = 起点 + s × (home − 起点)
```

三次插值的峰值速度是平均速度的 1.5 倍，所以 `--return-speed`（平均）与
`--return-max-peak`（峰值上限）各管一头，谁更紧谁决定时长。默认 10 deg/s 与
15 deg/s 恰好等价；峰值默认值 15 deg/s 远低于实测跟随能力 86 deg/s，所以默认配置
不会撞上限。

**默认回位与对齐快慢相当**：对齐默认 4 秒走完几十度（峰值约 14 deg/s），回位按
10 deg/s 平均、15 deg/s 峰值算，同样位移约 3.7 秒。空间紧、或想让回位更柔和时，
把这两个参数调小即可——**时长会自动变长，不需要另设时间**。

回位目标同样过 `clamp_targets`：home 若落在可指令范围外（例如启动时 follower 失能
下坠过），计划里会标出会被钳制的关节，运行中也会告警。`--max-step-deg` 不作用于回位
——回位是一条规划好的平滑轨迹，削它没有意义。

### Ctrl-C 之后机械臂仍在动

回位是**本工具唯一「按了键还在动」的行为**。操作者按下 Ctrl-C 后默认会认为机械臂
已经停下，而它还在往 home 走——这是真实的安全隐患，所以回位开始时会立即打印一行
醒目提示，包含预计秒数：

```
========================================================================
遥操作结束（Ctrl-C 中断）：正在回到初始位置，预计 3.6 秒；再按一次 Ctrl-C 可立即停下
========================================================================
```

即便有提示，**现场也必须为回位留出空间**：回位位移与对齐位移是同量级的（几十度），
不是小幅动作。

### 为什么程序要自己接管 SIGINT

rclpy 默认的 SIGINT 处理会在 Ctrl-C 时**立刻关闭上下文**，此后发布和订阅全部失效
（实测：`spin_once` 立即抛 `RCLError ... the given context is not valid`，话题不再
更新）。而回位恰恰发生在 Ctrl-C 之后，必须还能发指令、还能读使能状态。

所以本工具用 `rclpy.init(signal_handler_options=SignalHandlerOptions.NO)` 自己接管
SIGINT（退回 Python 默认行为：抛 `KeyboardInterrupt`），上下文一直活到回位结束。

代价：**SIGTERM（`kill`）不再触发回位**，它是立即终止进程。要回位就得用 Ctrl-C。

## 跟随速度：瓶颈是 `--speed`，不是固件限速（2026-09-23 实测判定）

### 结论先说

**把固件 `max_joint_spd` 从 300 放大到 1500 这件事，判定为不需要做。** 真正压住跟随
速度的是遥操作自己的 `--speed`（速度百分比）默认值：它早先是 **10**，即
`MotionCtrl_2(0x01, 0x01, 10)` = 整臂最大速度（3 rad/s ≈ 172 deg/s）的 10% ≈
**17.2 deg/s** —— 与 `max_joint_spd = 300` 的换算值**恰好相同**，所以两者长期没被区分开。

### 判别实验（真机，2026-09-23）

同一条臂、同一套拖动动作，只改 `--speed`，固件限位保持出厂值不动：

| 项目 | `--speed 10`（旧默认） | `--speed 100` |
| --- | --- | --- |
| follower 持续速度峰值（0.5s 窗口，六关节） | 17.4~19.0 deg/s（硬饱和） | **45.6~86.2 deg/s** |
| 与拖动速度的关系 | 拖快就必然滞后 | **跟着拖动走**：j1 45.6 / master 44.1、j2 70.3 / 75.6、j3 82.7 / 83.7 |
| 拖动速度 18.5% 时间超 17.2 deg/s，95 分位 34.6，峰值 176 | 滞后可达 76 度 | 只在最猛的几下（j4/j5/j6 的瞬时尖峰）差 15~25% |

`max_joint_spd` 全程是 300（17.2 deg/s），而 follower 跑出了 **86 deg/s 的持续速度**，
所以在这个控制路径上（CAN 流式位置指令 + `MotionCtrl_2` 百分比），它**不是运动速度的
硬上限**。因此：

- **不要写 flash。** 需要提速时改 `--speed` 即可，默认值已改为 **100**（不额外限速）。
- `max_joint_spd` 具体约束什么（加速度规划？过速保护阈值？）**尚未确认**，本手册不
  对它下结论。已读回的四台原值：`j2[−2.0, 180]`、`j3[−170, 2.0]`、其余出厂值，
  `max_joint_spd` 全为 300。
- 若将来确实需要改它，工具与回滚命令见下一节（保留备用）。

### 跟随质量实测（2026-09-23，50 秒真机运行，操作者持续拖动）

**操作者停下时能否收敛**（master 静止 >0.8 秒的段，取末段 0.3 秒的平均残差）：

| 关节 | j1 | j2 | j3 | j4 | j5 | j6 |
| --- | --- | --- | --- | --- | --- | --- |
| 残差（度） | 0.031 | 0.059 | 0.101 | 0.071 | 0.072 | 0.055 |

即**停下来就在 0.1 度以内对齐**（j3 的 0.101 度是软件限位比机械限位低的那一点，
见「对齐后仍有残差」一节）。

**拖动中能否跟上**（0.5 秒窗口的速度峰值，deg/s）：

| 关节 | j1 | j2 | j3 | j4 | j5 | j6 |
| --- | --- | --- | --- | --- | --- | --- |
| follower | 34.7 | 59.4 | 81.2 | 101.7 | 150.1 | 117.1 |
| master（拖动） | 35.6 | 57.7 | 74.9 | 108.5 | 136.7 | 120.3 |

follower 在腕部关节上能跑到 100~150 deg/s，与拖动速度同量级——**速度不再是瓶颈**。

**猛拉的瞬时滞后**：拖动峰值达 49~185 deg/s 时，残差瞬时可达 25~97 度（都在 master
仍处于可指令范围内的时刻，即纯滞后而非钳制），拖慢后约 1 秒内收敛回上面那 0.1 度。
这是物理限制：机械臂不能瞬间加速，`--speed` 已经开到 100 也没有更多余量。

**限位钳制**：操作者把 j3/j4/j5 拖出可指令范围时（j3 < −170 或 > +2、j4 超 ±100、
j5 超 ±70），follower 停在边界上（本次 j3 670 次、j4 142 次、j5 359 次）。这是设计
行为——可指令范围必须窄于机械限位。

**抖动**：操作者松手的那段里 master 无抖动（未持握）、follower 自身 0.011~0.041 度
（5~15 Hz），即 follower 不自生可见抖动；持握手抖的抑制见「跟随阶段的滤波」一节。

## 备用：`max_joint_spd` 的读写工具（**未在真机写入，判定不需要**）

四台臂的该字段目前仍是出厂值 300。工具留着备用——若将来换用别的控制模式（例如驱动器
内部轨迹模式）并发现它确实起作用，再按本节流程执行。`piper_speed_limit` 默认干跑
（只读取并打印计划），加 `--send` 才写入，写完立即逐台读回验证。

```bash
# 干跑：逐台读取当前限位并打印将要写入的内容（只发 0x472 查询帧）
ros2 run piper piper_speed_limit

# 真正写入（会改写驱动 flash）并读回验证
ros2 run piper piper_speed_limit --send

# 只处理一台
ros2 run piper piper_speed_limit --port can_fl --send
```

### 前置条件：该臂必须失能

写入本身不产生运动，但它会改变「越界指令被钳到哪里」，所以工具从各臂自己广播的
低压反馈帧读使能位，**未确认失能就拒绝写入**（`--allow-enabled` 可显式覆盖）。读取
使能位是完全被动的观测。

从臂当前若在使能状态，先失能再写：

```bash
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: false}"
ros2 service call /enable_srv_right piper_msgs/srv/Enable "{enable_request: false}"
```

### 写入内容与验证

每个关节一条 `0x474`（`MotorAngleLimitMaxSpdSet`），**三个字段全部显式给值**：角度
上限、角度下限都用**该台臂自己读回的原值**填充，只改 `max_joint_spd`。不能用
`0x7FFF`（"不修改"）——该语义只有固件 V1.5-2 之后支持，旧固件会把它读成
32767×0.001 = 32.767 rad/s，远超合法上限 3000。

写完逐台读回，要求：限速等于新值、角度限位与写入前逐位相同。任一项不符即报错退出。

**2026-09-23 干跑读回的四台原值**（写入前记录，用于回滚）：

| 接口 | 角色 | j2 | j3 | 其余关节 | max_joint_spd |
| --- | --- | --- | --- | --- | --- |
| `can_ml` | master_left | [−2.0, 180] | [−170, 2.0] | 出厂值 | 300 |
| `can_mr` | master_right | [−2.0, 180] | [−170, 2.0] | 出厂值 | 300 |
| `can_fl` | follower_left | [−2.0, 180] | [−170, 2.0] | 出厂值 | 300 |
| `can_fr` | follower_right | [−2.0, 180] | [−170, 2.0] | 出厂值 | 300 |

### 回滚命令

```bash
ros2 run piper piper_speed_limit --port can_ml --spd 300 --send
ros2 run piper piper_speed_limit --port can_mr --spd 300 --send
ros2 run piper piper_speed_limit --port can_fl --spd 300 --send
ros2 run piper piper_speed_limit --port can_fr --spd 300 --send
```

**每台都要用该台自己读到的原值**，不要照抄另一台——四台恰好出厂一致只是这次的运气。
写入成功后工具会再打印一遍逐台回滚命令（含各台写入前的原值）。回滚只改限速，角度
限位取自回滚那一刻读到的值，所以它**不会**把 2026-09-23 放宽过的 joint2/joint3 限位
一起改回去。

### 驱动查询行为（实测，2026-09-23）

**驱动一次只答一条限位查询**。在 `can_ml` 上实测：

| 查询方式 | 结果 |
| --- | --- |
| 逐条查询，每条等答复后再发下一条 | j1–j6 全部正确答复（约 3ms 内） |
| 6 条以 20ms 间隔连发 | 只回来 4 条，另有一条电机号字段为 0（解码拒绝） |
| 6 条连发更快 | 一条都不回 |

所以工具逐条查询、每条等到答复或超时、丢失则重发一次。读取失败时**不做部分写入**，
直接报错退出。

### 安全（现行默认值下必须知道的事）

`--speed` 默认 100 意味着**不再有软件限速**：实测 follower 的持续速度已经能到
86 deg/s，在腕部关节（j4/j5/j6）上属于较快，**猛拉 master 会让 follower 快速跟随**。
这不是将来才有的行为，是当前默认值下的行为。所有会让机械臂动的测试都需要操作者在
现场、工作空间内无人、急停可达，且任何运动指令发出前先确认整臂 ENABLED。

想让它慢下来就显式加 `--speed 50`（≈86 deg/s）或更小——那是有意的软件限速，代价是
拖快时必然滞后。

### 告警阈值从哪来

`piper_feedback.py` 里的 `MEASURED_MAX_JOINT_SPD_DEG_S = 86` 是回位计划里"峰值是否
超过实测跟随能力"提示的依据，取自上面那次真机实测（`--speed 100` 下的持续速度峰值
86.2 deg/s），**不是固件限位值**。若将来改动 `--speed` 默认值或机械负载，这个数需要
重新实测。

## 循环频率直接决定跟随延迟

程序每秒报告一次**实测循环频率**。它若低于 `--rate`，说明单次循环的处理耗时超过了
周期，跟随就会滞后。周期控制按累积截止时间休眠并扣除处理耗时，实测设定 50 Hz 能达到
50.0 Hz（早期用固定 `sleep(period)` 的做法只能到约 33 Hz，直接造成约 10 ms 的额外延迟）。
回位阶段用同一套周期控制，同样每秒报告实测频率。

另有一个上限在程序之外，但它**不是**固件的 `max_joint_spd`：真机实测表明压住跟随
速度的是 `--speed`（速度百分比），详见「跟随速度」一节。拖动 master 的速度超过
follower 实际能跑的上限时，必然滞后——这与频率无关。

## 对齐后仍有残差，这是物理限制

follower 无法 100% 复制 master 的姿态：**承重关节在失能时会下坠到机械限位上，而
follower 的软件限位必须略低于机械限位**，否则指令会指向不可达位置、让电机顶死。

实测（joint3 上限放宽到 2.0° 之后）：

| master 臂 | j3 静置 | follower 可到 | 残差 |
| --- | --- | --- | --- |
| `master_left` | +2.049° | +2.000° | 0.049° |
| `master_right` | +2.102° | +2.000° | 0.102° |

**0.05~0.10° 的残差对遥操作可忽略**（肘关节 0.1° 约合末端 0.5 mm）。放宽 joint3
上限之前这个残差是 0.848°，follower 完全无法匹配 master，所以那次放宽是必要的。

软件限位的安全依据：**关节实际到达过的角度必然机械可达**。+2.102° 是实测到达过的
值，所以任何不高于它的软件限位都不可能指向不可达位置。

限位的**最小步进是 0.1°**，所以只能取 2.0°（20）或 2.1°（21）这类整值。

## 必须知道的陷阱

### `auto_enable` 默认是 `true`

`start_single_piper.launch.py` 的 `auto_enable` **默认 `true`**，而节点的该分支会在
循环里反复调用 `EnableArm(7)` 和 `GripperCtrl`。给 master 启动节点时**必须显式传
`auto_enable:=false`**，否则会直接给 master 上电——而遥操作要求 master 可拖动。
`start_two_piper.launch.py` 已在更早的会话改为 `false`，这个还没改。

### master 节点把控制输入重映射到了 `/joint_states`

`start_single_piper.launch.py` 里 `('joint_ctrl_single', '/joint_states')` 用的是
**通用话题名**。master 一旦使能，门禁就会放行，任何在 `/joint_states` 上发布的节点
（例如 `joint_state_publisher`）都会驱动 master 运动。使能 master 前务必确认该话题
没有发布者：

```bash
ros2 topic info /joint_states    # 期望 Publisher count: 0
```

### 使能 master 并不能让它"可拖动且不下坠"

Piper 没有重力补偿/零力模式。实测：

| 尝试 | 结果 |
| --- | --- |
| `MotionCtrl_1(0,0,0x01)` 拖动示教记录 | 只把 `teach_status` 置为 `START_RECORDING`，`ctrl_mode` 仍是 `STANDBY`，**不使能、不提供重力补偿** |
| 使能 master | 刚性保持、不下坠，但**拖不动** |
| `MotionCtrl_2` 的 ctrl_mode | 只有 待机/CAN/以太网/wifi/离线轨迹，没有柔顺档 |

所以 master 保持**失能**、由人握住拖动是当前唯一可行的方式。人手一直握着它，它就不会
下坠；下坠只在松手时发生。

### CAN 掉线会让节点自己退出、机械臂随后失能（2026-09-23 实测）

> **本节引用的接口名是 2026-09-23 当时的命名**（当天左从臂叫 `can_fr`、今天叫 `can_fl`；
> 当天主臂叫 `can_fl`、今天叫 `can_ml`）。日志原文与统计数字按当时记录保留、未改写；
> 要对应到今天的实体，按序列号／USB 端口查 [`PI05_CAN_MAPPING.md`](PI05_CAN_MAPPING.md)
> 的「接口命名」一节。

现场跑一次性 50 秒验证时，左从臂突然不动了。事后查明：

1. **控制节点检测到掉线后主动退出**，它自己的日志末尾是
   `[ERROR] ... can_fr is loss` / `[ERROR] ... exit...`（判据是 SDK 的 `piper.isOk()`，
   节点随后调用 `rclpy.shutdown()`，没有 traceback）。节点一退出，`/joint_ctrl_cmd_left`
   就没有消费者了，指令再也到不了机械臂。
2. **机械臂随后处于失能**。节点的退出路径**并不**调用失能（`DisableArm` 只出现在使能服务的
   回调里），所以失能是**驱动器自己的失能保护**：指令流中断一段时间后它断开输出。这是
   fail-safe，不是故障状态——实测该臂其余一切正常（反馈帧 1200 帧/秒、母线 23.0V、
   FOC 34~36°C、六轴通信都在），只是输出被断开了。
3. **底层原因是 CAN 链路故障**，而且是 `can_fr` 这一条独有：同一台机器上
   `can_fr` 的统计是 `error-pass 3224、dropped 7082`，而 `can_fl`、`can_ml` 全为 0。
   该接口是 USB 适配器（`parentdev 1-13`），故障发生在一次大幅度快速拖动期间——
   先查这条链路的 USB 适配器与线缆（接触/屏蔽/终端电阻），换个 USB 口或换适配器对比统计。

**对工具的影响**：`piper_teleop` 会立刻发现（每秒报告里出现
`!! follower 使能异常：使能状态已过期`），并在结束时**拒绝执行回位**
（`回位中止：使能状态已过期，不发送任何指令`）——不掉线保护就是为这种情形做的。
此时机械臂已经不听指令，**唯一的处置是急停/断电检查链路**，而不是继续操作。

### Ctrl-C 不是"立刻停止"

见「结束回位」一节：Ctrl-C 之后 follower 还要走一趟回位轨迹。要它原地停住，按第二次
Ctrl-C，或者在启动时加 `--no-return-home`。

## 现场前提

1. 工作空间内无人，急停可达。
2. follower 的**整个**运动轨迹上无障碍物——对齐阶段有几十度的位移（本次 j4 达
   16.4°、j6 达 6.7°），**回位阶段同量级**，而回位发生在 Ctrl-C 之后，容易被忽略。
3. master 处于失能状态，由操作者握住。
4. 对齐期间（默认 4 秒）尽量别动 master：**握着一路拖不会"重新对齐"，程序会直接
   切进跟随**，此时偏差会由跟随快速补上——幅度就是你拖走的量，所以别在对齐时猛拉。
5. 全程保持只读监测旁路运行，例如 `ros2 run piper piper_joint_watch`。
6. 整臂 ENABLED 是发布运动指令的前提：工具在启动时、跟随中（每秒报告）与回位期间
   （每周期）都会校验，掉线会告警；回位期间掉线会直接中止。

## 退出

按 `Ctrl-C`。follower 会**先回位**到启动姿态（打印预计秒数），回位结束后它仍使能、
停在 home 上；再按一次 Ctrl-C 可中止回位、停在原地。`--duration` 到时的行为相同。

回位结束后应显式失能：

```bash
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: false}"
ros2 run piper piper_enable_check --port can_fl --expect disabled
```

## 完整 50 秒验证流程

一次可复现的验证由"记录 → 遥操作 → 分析"三步组成。记录与分析用
`piper_teleop_verify`（接收-only 套接字，全程不发送任何帧；它还会打印该用的遥操作
命令）。**不要用遥操作自己的输出做验证**：它每秒只打一行，而滞后、抖动、停顿都发生在
20~50 Hz 的尺度上；而且 50 Hz 的采样会把 5~15 Hz 的抖动混叠掉，必须用约 1200 帧/秒
的原始帧。

### 0. 环境（每开一个新终端都要做）

`~/.bashrc` 里只 source 了 ROS，**没有** source 这个工作空间，所以新终端里
`ros2 run piper ...` 会报找不到包。每个终端先执行这两行：

```bash
source /opt/ros/humble/setup.bash
source ~/piper_ros/install/setup.bash
```

**工具一律用 `ros2 run piper <工具名>` 启动。** ROS 2 不会把包的可执行目录加进 `PATH`，
直接写 `piper_teleop --side left` 会得到 `command not found`（实测，2026-09-23）。

如果刚拉过改动、或工具列表里没有要用的命令（例如 `piper_teleop_verify`），先构建一次。
用下面这条命令核对本包装了哪些工具：

```bash
ros2 pkg executables piper
```

构建：

```bash
cd ~/piper_ros && colcon build --symlink-install
```

构建是增量的，几秒钟；`--symlink-install` 让 Python 文件改动无需重新构建即可生效，
但**新增入口点（setup.py 里的 console_scripts）必须重新构建才会出现**。

### 0.1 前置检查（缺一不可）

```bash
# 四条接口都在、且能收到各臂的核心反馈帧
ros2 run piper piper_bus_probe

# 接口错误计数应当是 0（这一项曾抓到过一次 USB 适配器掉线：error-pass 3224）
ip -s -d link show can_ml; ip -s -d link show can_fl

# 节点在跑、从臂使能
ros2 node list
ros2 topic echo /arm_enable_status_left --once      # 期望 all_enabled: true
```

若接口名不对（例如某块适配器重插后变成 `can0`），先用仓库根目录的脚本按 USB 口重命名：

```bash
cd /home/mips/piper_ros && sudo bash can_muti_activate.sh
```

注意名字有**两个来源**：这个脚本按 USB 端口分配名字，而系统里的
`/etc/systemd/network/20-piper-can-*.link` 按适配器序列号分配。两者不一致时会出现
「名字都在、但对应错了臂」——2026-09-24 就是这么发现的。改完（或换过 USB 口 /
重插过适配器之后）用这条只读命令验收，四条都必须 `[OK]`：

```bash
ros2 run piper piper_pi05_can verify all
```

### 1. 起记录（第一个终端）

```bash
source /opt/ros/humble/setup.bash && source ~/piper_ros/install/setup.bash
ros2 run piper piper_teleop_verify --duration 70
# 默认记录 can_ml(master_left) 与 can_fl(follower_left) 到 /tmp/piper_teleop_verify.csv
# 记录时长要比遥操作长（遥操作 50 秒 + 启动 3 秒 + 对齐 4 秒 + 回位约 10 秒）
```

它会打印出下一步该执行的遥操作命令。

### 2. 起遥操作（第二个终端）并拖动

**新终端同样要先 source**（见第 0 步），否则找不到 piper 包：

```bash
source /opt/ros/humble/setup.bash && source ~/piper_ros/install/setup.bash
ros2 run piper piper_teleop --side left --enable --duration 50
```

看完"对齐完成 -> 进入绝对跟随"之后再开始拖 master，按下面三段做，**每段都要有**：

| 段 | 动作 | 目的 |
| --- | --- | --- |
| ① 按住不动 ≥10 秒 | 握住 master 尽量不动 | 量静止段的抖动与"手停着目标是否完全静止" |
| ② 慢拖 ≥10 秒 | 指尖慢慢推，约 1~3 deg/s | 量慢拖是否被切成台阶（"走一下停一下"） |
| ③ 大幅快拖 ≥10 秒 | 正常到较快速度来回拖几次 | 量滞后与急停过冲 |

50 秒到点后它会自动回位（约 3~10 秒，取决于位移），终端会打印预计秒数——**回位期间
机械臂仍在动**，要再按一次 Ctrl-C 才会立即停下。

### 3. 分析（记录结束后）

```bash
ros2 run piper piper_teleop_verify --analyze /tmp/piper_teleop_verify.csv
```

输出四组数：**按拖动速度分档的滞后**（中位数/90 分位）、**静止段的 5~15 Hz 抖动**、
**拖动中 follower 的停顿占比**、以及两臂帧率是否正常。判断标准：

| 指标 | 正常范围（2026-09-23 实测基线） |
| --- | --- |
| 帧率 | 每臂约 1200 帧/秒，逐秒波动 < 5% |
| 滞后 | 1~5 deg/s 档约 1.5 度；5~20 档约 2.5~2.9；20~80 档约 8 |
| 静止段抖动 | follower 0.01~0.04 度（机械臂自身本底；master 应为 0） |
| 停顿占比 | 1~5 deg/s 档约 30%（含操作者自己的停顿） |

**跨运行比较必须按同一速度档**，否则拖动内容的差异会盖过真实差别——2026-09-23 就因此
得出过一次错误的"滞后降了 6~10 倍"的结论。

### 4. 已在真机上验证过的结论（不必重复尝试）

| 试过的做法 | 结果 |
| --- | --- |
| 一阶低通（τ=0.02s）替代 One Euro | 8~12 Hz 手抖只衰减约 30%，弃用 |
| 每周期重规划五次多项式（静止到静止） | 匀速拖动时滞后发散（100 deg/s 时 59 度、150 时 389 度） |
| 同上加"可停速度上限" | 急停/反向时冲过目标 66~86 度 |
| 同上加目标速度前馈 | 每周期只走到曲线最平缓的开头，速度起不来 |
| 七段式 S 曲线（时间最优加速度 + jerk 限幅） | 同一流水线下滞后 3.65 度 vs 现行 2.00 度、抖动 0.088 vs 0.029——**两个方向都更差** |
| 提高 `--speed`（10→100） | **有效**：这曾是跟随速度的真正瓶颈（见「跟随速度」一节） |
| 死区只按幅度 | **有害**：慢拖被切成 0.2 度台阶（"归零再加速"），已改为幅度+速度门限 |

最后两项是有效的改动，其余都已被数据否决。**跟随滞后的 60~95% 发生在"指令 → 机械臂"
这一段**（实测：1~5 deg/s 档占 60%，80 deg/s 以上占 95%），属于驱动器执行侧，任何
指令侧插值都改不到它；能动的只有驱动器参数（`JointConfig` 0x475 的最大关节加速度）
或提高指令频率，两者都要单独评估。

## 参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--side` | `left` | 驱动哪台 follower |
| `--master-topic` | `/joint_states_single` | master 关节角度话题 |
| `--align-seconds` | 4.0 | 对齐时长；位移不变时它直接决定速度（4 秒 ≈ 2 倍速） |
| `--max-step-deg` | 0（关闭） | 削掉信号跳变；默认关闭以保证同步 |
| `--speed` | 100 | follower 速度百分比 1–100；节点把它转发给 `MotionCtrl_2`，是**对整臂最大速度（3 rad/s ≈ 172 deg/s）的缩放**。100 = 不额外限速，改小它等于加一道软件限速 |
| `--rate` | 50 | 发布频率 Hz（跟随与回位共用） |
| `--filter` | `alpha-beta` | 跟随阶段滤波方案：`alpha-beta` / `one-euro` / `lowpass`（对照）/ `none` |
| `--alpha-beta-alpha` | 0.84 | α-β 位置残差增益；由重复误差极点 λ=0.40 推导 |
| `--alpha-beta-beta` | 0.36 | α-β 速度残差增益；由重复误差极点 λ=0.40 推导 |
| `--alpha-beta-max-dt` | 0.1 | 采样间隔超过此值时清零旧速度并以新测量重新锚定，秒 |
| `--deadband-deg` | 0.2 | 死区幅度阈值，度；0 关闭死区 |
| `--deadband-speed` | 0.8 | 死区速度门限 deg/s：低于它才认为手停着；0 表示只按幅度保持 |
| `--smooth-bandwidth` | 15 | 五次插值平滑的带宽 rad/s；0 关闭这一级 |
| `--smooth-max-velocity` | 172 | 平滑级的速度上限 deg/s |
| `--smooth-max-acceleration` | 6000 | 平滑级的加速度上限 deg/s² |
| `--smooth-max-jerk` | 60000 | 平滑级的 jerk 上限 deg/s³ |
| `--one-euro-min-cutoff` | 1.0 | One Euro：静止时的截止频率 Hz |
| `--one-euro-beta` | 0.3 | One Euro：截止频率随速度的增长 Hz per deg/s |
| `--one-euro-d-cutoff` | 1.0 | One Euro：速度估计自身的截止频率 Hz |
| `--filter-tau` | 0.02 | 仅 `--filter lowpass` 使用：时间常数，秒 |
| `--return-speed` | 10 | 回位平均速度 deg/s |
| `--return-max-peak` | 15 | 回位峰值速度上限 deg/s |
| `--no-return-home` | 关 | 结束时停在原地，不回位 |
| `--enable` | 关 | 不加则干跑，只打印不发送 |
