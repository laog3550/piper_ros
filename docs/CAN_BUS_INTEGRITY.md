# 两 CAN 总线完整性排查

> 下文的负载与错误记录针对旧 `0xFC + 0x20` 上位机桥接配置。
> 当前官方 `0xFA/0xFC` 方案见[操作说明](OFFICIAL_NATIVE_TELEOP.md)。

## 1. 结论摘要（2026-09-30 实测）

在**四台臂都通电、六关节全部失能、上位机不发送任何帧**的条件下测量两条总线：

| 总线 | 普通帧 | 估算负载 | 共享 ID | CAN 错误帧 |
| --- | ---: | ---: | ---: | --- |
| `can_left` | 6181/s | 686～834 kbit/s（1 Mbit/s 的 69%～83%） | 12 个 | 60 s 窗口实测 586 个（9.77/s），另一次 60 s 实测 0 个 |
| `can_right` | 6181/s | 686～834 kbit/s（69%～83%） | 20 个 | 8 s/20 s 窗口实测约 283/s 与 665/s，另一次 60 s 实测 0 个 |

三条结论：

1. **负载没有余量。** 两 CAN 拓扑把两台臂塞进一条总线，光是臂自己的反馈就占到 69%～83%；
   我们自己的控制流（200 Hz × 5 帧 ≈ 1000 帧/秒）还要再加约 135 kbit/s（+13%），
   最坏情况会顶到约 96%。总线接近饱和时，任何电气余量不足都会被放大成错误帧与延迟。
2. **共享 ID 无法通过配置消除。** 每条总线上有 12（左）／20（右）个 ID 同时被两台设备
   发送：`0x251`～`0x256` 各约 400 Hz、`0x261`～`0x266` 各约 80 Hz（右侧还有未偏移的
   `0x2A1`～`0x2A8` 各约 400 Hz）。固件的驱动反馈族不随 `0x20` 偏移搬移（14.7 已确认），
   所以只能靠**物理分开**解决。
3. **错误帧是间歇的，不是常数。** 同一条总线在不同时刻分别测到 0/s、~10/s、~283/s、
   ~665/s。这更像"边缘条件下的偶发"，而不是某个确定的软件缺陷；因此每次测量都必须
   记录条件，并用 60 s 以上的窗口判读。

另外两条工具层面的实测结论，排查时不要踩：

- **错误帧只交付给显式打开 `CAN_RAW_ERR_FILTER` 的套接字。** 本机 can-utils 2020.11 的
  `candump -e` 在同样条件下报 0 个错误帧（实测 49441 行普通帧、0 行错误帧），而
  `piper_can_quality`（python-can 自动打开该过滤器）和裸套接字都能看到。**基线统计请用
  `piper_can_quality`，不要用 `candump -e` 下结论。**
- 两个适配器都是 candleLight（USB `1d50:606f`），都挂在 **Bus 01** 上，链路各自协商为
  **12 Mbit/s 全速**（`lsusb -t` 显示 `12M`）。全速是 candleLight 的正常形态，不是故障；
  但两台设备共享同一个上游控制器，排查时要把"换口/换线"作为变量之一。

## 2. 负载构成

左总线（`can_left`，主臂已偏移 `0x20`）：

| 帧族 | 实测帧率 | 是否共享 ID | 说明 |
| --- | ---: | --- | --- |
| `0x1C0`～`0x1C3`、`0x212`（末端/手） | 101/s | 否 | Revo2 反馈，20/40 Hz |
| `0x251`～`0x256` 高速关节反馈 | 2400/s | **是**（2×200 Hz） | 每台臂各 200 Hz |
| `0x261`～`0x266` 低速驱动反馈 | 480/s | **是**（2×40 Hz） | 使能位来源 |
| `0x2A1`～`0x2A8` 从臂高速反馈 | 1600/s | 否 | 8 个 ID × 200 Hz |
| `0x2C1`～`0x2C8` 主臂高速反馈 | 1600/s | 否 | 偏移 0x20 后的主臂反馈 |

右总线（`can_right`，**尚未配置偏移**）：`0x2A1`～`0x2A8` 变成 3200/s（两台各 200 Hz），
即从臂反馈族本身也成了共享 ID，共享 ID 总数 20 个。

单台臂一条总线时，同样的组成会降到约 3140 帧/秒（约 350～430 kbit/s，35%～43%），
再叠加我们的控制流仍在 50% 上下，才是有余量的形态。

## 3. 机制

处于"两台设备发同一个 CAN 帧 ID"的状态时：两帧的仲裁 ID 相同，仲裁阶段分不出胜负，
进入数据段后只要载荷有一位不同，落后的那台就会检测到位错误并发出错误帧，两帧都被
作废并稍后重传。这就是：

- 为什么**共享 ID 越多，错误帧越多**（`can_right` 20 个共享 ID 时的错误率明显高于
  `can_left` 的 12 个）；
- 为什么**适配器自己的内核计数始终是 0**（`bus-errors`、`error-warn`、`error-pass`、
  `bus-off`、丢帧全为 0）：发出错误帧的是碰撞中的臂，我们只是收报方；
- 为什么负载高会放大它：接近饱和时发送被推迟，两台同 ID 设备"同时起步"的概率上升。

## 4. 工具与命令

```bash
# 单轮体检（默认 20 s）
ros2 run piper piper_can_quality --port can_left --seconds 60

# 连续三轮，看间歇性（每轮一行可对比摘要）
ros2 run piper piper_can_quality --port can_left --seconds 60 --repeat 3
```

输出包含：分组帧率、估算负载（标称/最坏情况）、共享 ID 清单、错误帧总数/平均/单秒峰值/
状态退化帧数、错误类别与 data、以及"错误帧前后 ±300µs 内出现的 ID 相对基线占比的过代表
倍数"（用来判断是哪些流量在冲突）。

测量前请记录条件：哪几台臂通电、六关节使能状态、是否有人进入示教、主机上有哪些
Piper/ROS 进程、刚做了什么（插拔、上电、改线）。

## 5. 排查步骤（每步都写明判读标准）

**步骤 1：基线。** 四台臂通电、全部失能、无任何控制进程，两条总线各测 3 × 60 s。

- 判读：记录错误率范围。目前已知它会在 0/s 与数百/s 之间波动，所以只测一次没有意义。

**步骤 2：单臂隔离（决定性实验）。** 把 `follower_left` 断电（只留 `master_left` 在
`can_left` 上），再测 `can_left`。

- 判读：
  - 共享 ID 应从 12 个降到 0（`0x251`～`0x256` 从 400 Hz 降到 200 Hz、`0x261`～`0x266`
    从 80 Hz 降到 40 Hz），负载降到约 43%；
  - **错误帧应降到 0**。若错误帧仍然出现，说明当前错误不是"同 ID 碰撞"造成的，而是
    电气/适配器/线缆问题（终端电阻、支线、屏蔽、供电、USB 链路），按步骤 4 的方向查；
  - 若错误帧降到 0，则同 ID 碰撞就是主因，处置见第 6 节 A/B。

**步骤 3：换另一台单臂。** 断电 `master_left`、给 `follower_left` 上电，重复步骤 2。

- 判读：与步骤 2 相同。两次结果不一致时，问题更可能在**那一台臂或它的支线**上。

**步骤 4：适配器与链路互换。** 把左右两个适配器对调（或换 USB 口/换 USB 线），再测。

- 判读：错误跟着**适配器**走 → 查那个适配器；跟着**总线/臂**走 → 查线缆与臂；
  两边都变了 → 查公共因素（供电、接地、主机 USB 控制器）。

**步骤 5：物理检查清单**（每条都做成一次"改前/改后各测 60 s"的对照）：

- 主干两端各一个 **120 Ω 终端电阻**（两条总线都要；总线只在两端有终端，中间设备不接）；
- 支线（stub）尽量短（1 Mbit/s 下建议 ≤ 0.3 m），CANH/CANL 走**双绞**、不要与电机动力线
  并行走线；
- 所有节点**共地**，屏蔽层**单端接地**；
- 臂与适配器的供电是否稳定（示波器/万用表看 24 V 在使能瞬间是否跌落）；
- USB：换口、换线、避开与相机同一 hub；观察 `lsusb -t` 的 `12M/480M` 与 `dmesg` 有无
  USB 复位/溢出；
- 重复步骤 1 的基线测量，并记录每条改动各自的增量效果。

**步骤 6：带控制流复测。** 物理层改动完成后，用 `piper_two_can_align` 的静止目标发帧探针
（`--send --workspace-clear`，它只发从臂标准地址、且先在起点冻结 0.5 s）验证"加入控制流
后错误率是否仍然可控"，再进入阶段 D。

## 6. 处置选项

**A. 一台臂一条总线（推荐）。** 需要**再买两个 USB-CAN 适配器**（现有两个是 candleLight
`1d50:606f`）。收益：共享 ID 归零、每条总线负载降到 35%～43%、主臂与从臂在电气上互不
影响（主臂那侧的扰动不会打断从臂的指令流）。软件侧：直接 SocketCAN 的控制环本来就不经过
ROS 话题，改成"读一条总线、写另一条总线"是小改动，并且可以与固件直连方案共存。

**B. 保持两条总线，降低负载。** 两条路同时走：
- 向厂商确认 `0x251`～`0x256` 与 `0x261`～`0x266` 能否降频或关闭其中一族（这是唯一能真正
  减少共享流量的办法）；
- 软件侧压缩我们自己的控制流：把每周期 5 帧（`0x151` + `0x155`～`0x157` + `0x159`）压到
  3 帧（模式帧只在进入/切换时发、夹爪只在目标变化时发），并把命令频率从 200 Hz 降到
  100 Hz，可省约 9% 负载。
  即使这样仍有 12/20 个共享 ID，**只能减轻，不能消除**。

**C. 维持现状 + 放开错误帧策略（软件侧已生效）。** 只有在物理层确认"错误帧不会引起状态
退化、也不影响跟踪质量"时才可接受：要求 `状态退化帧 = 0`、60 min 连续运行的平均错误率
稳定、跟踪误差无异常。这一条必须与 A 或 B 并行推进，不能单独作为长期方案。

## 8. 与软件门禁的关系

`piper_two_can_teleop` / `piper_two_can_align` / `piper_two_can_identity` 默认使用
`recoverable` 错误帧策略（2026-09-30 决定）：容忍孤立错误帧，只在**状态退化**
（bus-off、错误被动、总线错误）或**持续速率超限**（默认 5 s 窗口平均 > 20 Hz）时中止。
需要回到最严口径时加 `--error-policy strict`。

摇操与管理器的 `--gate-profile relaxed` 把持续速率门限提高到 `50 Hz`，用于容忍
当前总线已经观测到的间歇突发；其他 CAN 状态退化仍立即中止。也可用
`--max-error-rate-hz` 显式覆盖该门限。总线体检工具与独立身份检查的默认值不随
摇操预设改变。

也就是说：物理层没有弄好之前，软件不会再因为偶发错误帧拒绝启动，但会持续把错误率写进
`/teleop/state` 与 `/diagnostics`；物理层的验收目标是让这些计数长期稳定在 0 附近。

## 9. 双臂不限时测试停流复查（2026-10-04）

右主臂已完成 `0x20` 反馈地址偏移，因此本次两条总线各有 12 个共享 ID，
不是第 2 节记录的右侧未配置时期的 20 个。双臂以 `50 Hz` 跟随时，
左侧在 15:32:09 锁存“六关节快照不同步：跨度 0.010s”，双侧联锁随即停流；
左侧此前累计记录 66 个 CAN 错误帧，故障前一次周期状态显示错误率 `8.8 Hz`、
主臂反馈 `196 Hz`、从臂反馈 `200 Hz`。右侧累计 26 个错误帧，但未先触发故障。
`0.010s` 是旧日志保留三位小数后的值；真实跨度超过 `10 ms` 门限，旧日志不能
区分主臂还是从臂的三组角度帧。故障后固定目标回位完成，两侧保持使能待机。

回位后的两侧只读复查分别进行 `45 s` 角度帧时序采样和 `60 s` 总线体检。
两条总线角度帧均约 `200 Hz`，采样时没有错误帧，也没有一次三帧跨度超过
`10 ms`。`60 s` 体检两侧各约 `6181` 普通帧/秒，估算占用 `686～834 kbit/s`
（最坏约 `83%`），各有 12 个共享 ID：`0x251～0x256`、`0x261～0x266`。
本次静止窗口均为 0 错误帧，说明故障是间歇现象；高占用和共享 ID 提供了
可能的延迟/重传机制，但尚未证明本次具体错误帧来自同 ID 冲突，
也不能排除电气干扰或主机收帧调度延迟。故障时未记录内核时间戳逐帧轨迹，
因此不能把错误帧与哪一组角度帧延迟逐帧配对。

软件诊断已增强：下次三帧跨度超限会给出主臂或从臂、实际毫秒值、
最旧与最新的角度反馈 CAN ID。`10 ms` 同步门限保留；ACTIVE 阶段遇到短暂
不同步时跳过当周期目标，恢复同步后继续，连续不同步达到 `100 ms` 则停流。
反馈过期、身份与使能异常、指令限位等检查仍保留。
物理根因的关键对照仍是第 5 节的左侧单臂隔离体检：
同条件下依次只留主臂、只留从臂，分别测共享 ID、总线占用和错误帧。

## 10. 2026-10-08 不限时摇操中断

双侧 `50 Hz` ACTIVE 运行中，左侧 CAN 错误帧总数从 `294` 增至 `338`、
`365`，最终在 `5 s` 滚动窗口达到 `20.2 Hz`，超过默认 `20.0 Hz` 门限。
错误类别为 `CAN_ERR_PROT | CAN_ERR_CRTL`；未出现 bus-off、error-passive 或
总线状态退化。左侧随即故障停流，右侧当时错误帧为 `0`，由双侧联锁停流。
两侧主从反馈在故障前仍约为 `200 Hz`，因此本次直接停流条件不是反馈丢失。

两只从臂固定目标回位完成后，两条总线同时进行了 `60 s` 只读体检，结果已记入
第 7 节：错误帧均为 `0`，但最坏估算负载仍为 `83%`、共享 ID 各为 `12` 个。
内核接口保持 `ERROR-ACTIVE`，控制器累计 `bus-off`、`error-pass`、
`bus-errors` 均为 `0`。这组结果确认错误突发具有间歇性，只能把高负载与共享 ID
列为机制候选，不能单凭本轮数据认定具体物理根因。下一步仍应做左侧主臂和
从臂分别单独通电的同条件对照，并检查终端电阻、接头、屏蔽与供电完整性。

## 11. 右侧主从臂隔离对照（2026-10-08）

在全部失能、上位机不发送控制帧的条件下，按“主从同时接入 → 仅主臂 → 仅从臂 →
主从重新接入”顺序各采样 `60 s`。仅主臂时普通帧 `3141/s`、最坏负载 `42%`，
仅从臂时 `3040/s`、`41%`；两种单臂条件都没有共享 ID，结论为 `CLEAN`。
主从同时接入的前后两轮均恢复为 `6181/s`、最坏负载 `83%`，并稳定出现
`0x251～0x256` 与 `0x261～0x266` 共 `12` 个共享 ID，结论为 `OVERLOAD`。

四个窗口的错误帧和状态退化帧均为 `0`。因此该实验已经证明高负载与 12 个共享 ID
由主从组合接入造成，并且单独任一设备时总线负载约减半；但错误风暴具有间歇性，
本次没有复现，不能仅据此确认共享 ID 就是错误帧的唯一物理原因。随后执行的失能
控制流对照见第 12 节。

## 12. 右侧失能控制流对照（2026-10-08）

右侧主从臂同时接入并保持失能，以注入开始时的右从臂六关节和夹爪反馈作为固定目标，
按摇操 ACTIVE 阶段的格式连续发送 `0x151`、`0x155`、`0x156`、`0x157`、`0x159`，
频率为 `50 Hz`。注入器逐帧检查复用的 `0x261～0x266` 低速反馈；任何 enabled
样本或严重 CAN 状态都会立即终止。停止后发送一帧 standby，并再次只读检查
`can_left`、`can_right`。

完整同步窗口持续 `60.000 s`，共发送 `3001` 个周期、`15005` 个控制帧，实测
周期频率 `50.016 Hz`。独立的 `65 s` 质量监测完整覆盖预检、注入和停止阶段，
普通帧从无控制流基线的 `6181/s` 增至 `6412/s`，最坏估算负载从 `83%` 增至
`87%`，其他帧组增加到 `231/s`；共享 ID 仍为 `0x251～0x256` 和
`0x261～0x266` 共 `12` 个。整个窗口错误帧、状态退化帧均为 `0`，所有可见
低速反馈持续为 disabled。停止后的双接口 `3 s` 只读检查也均为 `DISABLED`；
`can_right` 保持 `ERROR-ACTIVE`，内核累计 `bus-errors`、`error-pass`、
`bus-off` 仍均为 `0`。

此前另有一轮完整 `60 s`、`3001` 周期的同格式注入，注入端同样观察到 `0` 个
错误帧；该轮独立质量监测只覆盖了部分控制流，因此不作为负载数值依据。两轮结果
表明：增加摇操同频控制流确实把右侧最坏估算负载提高约 `4` 个百分点，但在当前
失能条件下没有复现 `CAN_ERR_PROT | CAN_ERR_CRTL`。因此不能认定错误只由控制流
增加触发；现有证据更符合“高基线负载、共享 ID 与机械臂运行状态共同参与的间歇性
时序问题”，仍需用更长窗口或启用但固定目标的分级实验区分使能状态与实际运动的
影响。

## 13. relaxed 门限下的不限时摇操中断（2026-10-08）

双侧完成使能和对齐后，于 `16:11:55` 进入 `50 Hz` 实时跟随；`16:21:15`
右侧锁存故障，ACTIVE 持续 `560.1 s`，约 `9 min 20 s`。本次没有运行时限，
也没有进程崩溃或反馈中断：故障前两侧主臂、从臂角度反馈均约为 `200 Hz`。

右侧错误帧具有明显突发性。故障前最后几秒，累计计数依次为
`404 → 458 → 470 → 489 → 550`，对应日志滚动速率
`0.0 → 10.8 → 13.2 → 17.0 → 29.2 Hz`；随后不到一秒内，`5 s` 窗口达到
`50.2 Hz`，超过 relaxed 门限 `50.0 Hz`，错误类别仍为
`CAN_ERR_PROT | CAN_ERR_CRTL`。右侧因此停止目标流并进入故障锁存，左侧由双侧
联锁停止。此前运行中已经出现过多轮低于门限的错误突发，所以用户感知为长时间正常
后突然中断，实际是最后一轮突发刚好越过停止阈值。

故障后的显式 stop 成功重新取得两侧 CAN 写锁并返回各自冻结起点；两侧回位核对、
新的实体示教释放确认、整侧失能和失能读回均完成，最终状态为 `IDLE_DISABLED`。
随后再次执行双接口 `3 s` 只读检查，`can_left`、`can_right` 均为 `DISABLED`；
两条接口保持 `ERROR-ACTIVE`，内核累计 `bus-errors`、`error-pass`、`bus-off`
均为 `0`。

结合第 12 节的全失能固定目标实验，可排除“增加 `50 Hz` 控制流本身必然触发错误”。
当前差异集中在使能状态、动态目标和实际运动，其中至少一个条件参与了错误复现；
现有日志尚不能在这三个条件之间继续归因。

## 14. 左右对照归因与处置顺序（2026-10-08）

第 13 节的逐秒日志重新按两侧会话轨迹配对后，所谓“正常左侧”在同一轮也累计了
约 `240` 个 `CAN_ERR_PROT | CAN_ERR_CRTL`，只是任一 `5 s` 窗口都没有越过
`50 Hz`；故障侧累计至少 `550` 个并在最后一轮突发越线。因此左右差异是突发强度，
不是“左侧无错误、右侧有错误”。两侧均使用 candleLight `1d50:606f`、`gs_usb`
和相同的 `1 Mbit/s` 位时序，分别直连同一个 xHCI 根控制器的不同 USB 端口；故障窗口
没有 USB reset、disconnect 或 overflow 内核日志。

全部失能时又同步采样共享 ID `20 s`。两侧每个 `0x251～0x256` 均约为 `400 Hz`，
每个 `0x261～0x266` 均约为 `80 Hz`，而且同一 ID 能看到来自两台臂的两种不同载荷。
这确认了每条总线上都有两个独立发送器在相同 CAN ID 下工作。失能窗口里两个发送时钟
当前错开，所以错误为 `0`；运行中时钟相位、驱动状态和总线排队变化后，发送窗口偶尔
重叠，数据段不同便产生协议/控制器错误帧和重发。错误突发并不总与快速运动同步：日志
里已有目标连续一个采样周期不变而错误计数仍增加的窗口。

现有证据按解释力排序如下：

1. **同 ID 双发送者叠加高占用**最符合全部结果。单独任一臂时负载为 `41%～42%`、
   共享 ID 为 `0`、错误为 `0`；两臂合并后为 `83%` 和 `12` 个共享 ID，加入
   `50 Hz` 控制流后约为 `87%`。左右两侧都出现同类错误，只是相位不同造成强度差异。
2. **使能状态会放大复现概率，但不是已证明的独立根因。** 全失能固定目标注入两轮未
   复现；历史记录又表明实体模式切换时即使没有上位机目标流也能出现错误。使能后驱动
   反馈载荷变化，足以改变同 ID 重叠时的位冲突结果。
3. 上位机 `50 Hz` 控制流、USB 端口、反馈陈旧和运行时限均不能单独解释本次中断。
   它们可改变余量或停止时机，但不是目前的首要根因。

在只保留两条物理 CAN 的约束下，不应继续运行“两台臂均为 `0xFC`”作为长期方案。
官方双臂方案把主臂配置为示教输入臂 `0xFA`，把从臂配置为运动输出臂 `0xFC`；主臂
只发送 `0x151`、`0x155`～`0x157`、`0x159`，从臂发送完整反馈。该角色非对称设计会
直接移除目前两套 `0x251～0x266` 反馈发送者中的一套。Windows 上位机证明的是这种
总线角色方案可行，不是 Windows 能容忍两台 `0xFC` 的同 ID 发送冲突。

双 CAN 处置顺序改为：

1. 优先验证第 15 节的 `0xFA + linkage_offset=0x20` 上位机桥接方案。它同时保留软件
   限幅、故障锁存和同会话固定目标回位。
2. 官方原生 `0xFA/0xFC` 直连随动可作为对照基线，验证错误帧和总线负载是否消失；
   但主臂会直接持续控制从臂，不满足当前自动回位状态机对控制权切换的要求。
3. 仅降低上位机目标频率、按变化发送 `0x151/0x159`、固定固件版本以跳过自动查询，
   只能减少额外流量或查询冲突，不能消除两台 `0xFC` 的十二组同 ID 发送者。
4. 不通过提高错误率门限掩盖故障。bus-off、error-passive、反馈陈旧和持续错误突发仍
   必须立即锁存。

下一次运行日志已增加 `[left]`、`[right]` 前缀，并按错误类别累计计数，避免再依靠
交错输出推断故障侧。该改动只增强诊断，不改变门限、控制频率或运动行为。

## 15. 官方角色非对称与双 CAN 改进方案（2026-10-10）

官方 [`double_piper.MD`](https://github.com/agilexrobotics/piper_sdk/blob/master/asserts/double_piper.MD)
的每侧拓扑仍是一只 CAN 模块连接一对主从臂，但角色配置为：

```text
主臂：MasterSlaveConfig(0xFA, 0, 0, 0)
从臂：MasterSlaveConfig(0xFC, 0, 0, 0)
上电：先从臂，后主臂
```

官方同时明确：`0xFA` 主臂只发送五类控制帧，从臂发送控制帧之外的反馈。这与本项目
当前 `0xFC + 0x20` 主臂仍发送完整驱动反馈的行为不同，也解释了官方双 CAN 方案为何
不会形成当前观测到的两套 `0x251～0x266`。

### 15.1 保留自动回位的主机桥接变体

建议隔离配置主臂为：

```text
linkage_config = 0xFA
feedback_offset = 0x20
ctrl_offset = 0x20
linkage_offset = 0x20
```

从臂保持：

```text
linkage_config = 0xFC
feedback_offset = 0x00
ctrl_offset = 0x00
linkage_offset = 0x00
```

`linkage_offset=0x20` 按官方
[`0x470` 定义](https://github.com/agilexrobotics/piper_sdk/blob/master/piper_sdk/piper_msgs/msg_v2/transmit/arm_master_slave_config.py)
把主臂产生的联动控制目标从 `0x15x` 移到 `0x17x`。
上位机监听 `0x171/0x175～0x177/0x179`，完成钳制、滤波和状态机处理后，以
`0x151/0x155～0x157/0x159` 控制从臂。这样 ACTIVE 阶段仍由上位机持有唯一的从臂
控制发送权；进入 RETURNING 后停止 `0x17x → 0x15x` 转发，继续发送冻结起点的
`0x15x`，主臂仍在产生的 `0x17x` 不会覆盖回位目标。

该方案在协议定义上成立，但还没有在本机固件上验收。特别需要隔离主臂核对：

- `0xFA + linkage_offset=0x20` 后完整反馈和 `0x251～0x266` 是否确实停止；
- 实体示教进入、保持和退出期间是否只出现预期的 `0x17x`；
- 是否存在任何周期 `0x471 07 02`；若存在，该方案不能满足最终失能读回；
- 退出实体示教后，主臂控制帧是否停止或保持无害，广播失能是否能够稳定保持；
- 单侧两臂合并后，60 分钟只读和动态随动是否均为零错误帧、零状态退化。

当时的上位机桥接入口只接受 `0x2Cx` 主臂反馈，并把 `0x17x` 视为外部控制流；
该历史桥接变体尚未实现。当前入口改为官方零偏移原生联动，见
[操作说明](OFFICIAL_NATIVE_TELEOP.md)。任何 `0x470` 配置试验仍须先隔离目标臂。

### 15.2 不改变角色配置时可做的改进

若暂时保持两台 `0xFC`，可按官方
[`agx_arm_ros` 说明](https://github.com/agilexrobotics/agx_arm_ros/blob/ros2/README_EN.md)
固定 SDK 的 `fw_version` 以避免两台臂同时响应自动版本查询，
并减少模式帧和夹爪帧的重复发送；也可按官方顺序先上电从臂、后上电主臂，观察周期
相位是否更稳定。这些措施适合作为诊断和短期降险。它们不会改变两台臂持续发送相同
低速反馈 ID 的事实，因此不能作为长期故障闭环。

## 16. 官方原生联动改造后的只读复查（2026-10-11）

用户确认左右两侧各自的主、从臂接在同一条 CAN，左侧两臂已上电；右主臂上电后会进入
可拖动的重力补偿状态，按实体示教按钮后状态未变化，本次上电顺序尚不确定。
两只 USB-CAN 的序列号、端口、接口名及 `1 Mbit/s` 波特率与映射文件一致，接口均为
`UP / ERROR-ACTIVE`，内核 CAN 错误计数为 `0`。

| 接口 | 10 秒只读结果 | 判断 |
| --- | --- | --- |
| `can_left` | `0` 帧 | 已上电机械臂的 CAN 数据没有到达该适配器；无法仅凭此区分接线、供电控制器和角色状态。 |
| `can_right` | `30401` 帧、`20` 个 ID；默认反馈齐全，`0x2A1=0x00`，六关节使能；无 `0x15x` 或 `0x17x` 控制帧 | 只观测到一套反馈臂，未确认右主臂产生官方联动输出。 |

之前的 `0xFC + 0x20` 两臂同侧只读记录约为 `6181` 帧/秒，而本次左侧为 `0`、
右侧约为 `3040` 帧/秒；现有证据不能将变化单独归因于角色配置。
本次没有发送配置、使能、失能或运动帧。下一步需要在设备获得支撑、停止运动并断电后，
分别隔离主臂和从臂的 CAN 连接做只读抓包，并核对官方“先从臂、后主臂”上电顺序。

用户随后将左主臂断电，并确认左从臂仍上电且 CAN 线已接入 `can_left`。继续只读
观察 `8 s`，结果仍为 `0` 帧。`can_left` 保持 `UP / ERROR-ACTIVE`，RX、TX、
总线错误计数均为 `0`。单臂隔离后仍完全静默，当前无法仅凭总线数据区分
从臂固件角色异常与 CAN 物理链路故障；不应发送 `0x470` 或 `0x471` 试探。
左从臂随后单独断电重启，左主臂仍断电；重启后再观察 `10 s`，`can_left`
仍为 `0` 帧，接口 RX、TX 和 CAN 错误计数保持 `0`。单纯重启左从臂没有恢复
反馈。用户确认左从臂此时没有使能，也没有重力补偿，且左侧 CAN 线近期没有
拆接或改线。复核官方资料后更正前述物理链路推断：`0xFA` 输入臂可能只发送
控制帧，因此单臂静默还可能是左从臂角色被错误配置、处于不发送控制帧的状态；
当前没有读取到该臂保存的 `0x470` 参数，不能直接判为接线故障。

本机命令历史曾对 `can_right` 尝试 `0xFA + 0x20/0x20/0x20` 配置，参数与本次
官方默认零偏移方案不同；历史右侧方向抓包还曾观察到外部 `0x17x` 与重复的
`0x471 07 02`，足以解释当时失能被覆盖。命令历史本身不能证明配置成功或
代表当前状态。当前只读抓包只有一套默认反馈，未见这些控制帧。下一步应先核实
每台臂实际角色和对应接口，再考虑任何配置或使能操作。

再次进行两接口同步只读观察 `60 s`，期间用户仅给左从臂断电约 `5 s` 后上电。
`can_left` 全程 `0` 帧，`can_right` 始终约 `3040` 帧/秒且未随断电下降；
两条接口均未观察到控制帧。随后 `2 s` 复查显示 `can_right` 仍为一套默认
`20` 个反馈 ID（`6081` 帧），`can_left` 仍为 `0`。这排除了“当前右侧
反馈其实来自左从臂”的简单接口错配解释；仍不能只凭静默判断左从臂保存的角色。

随后在左从臂保持上电时给左主臂上电，同时监听两接口 `50 s`：
`can_left` 全程 `0` 数据帧、`0` 错误帧；`can_right` 稳定约 `3040` 帧/秒，
只有一套默认反馈 ID，无 `0x15x/0x17x` 控制帧。左主臂上电也没有让任何一条
接口出现左侧反馈或控制流。当前只读软件证据无法进一步区分左侧两台设备的
固件角色、控制器启动状态与到适配器的实际链路状态。
用户确认左主臂上电后没有自动进入重力补偿，左从臂仍未使能且没有姿态变化；
这与只读抓包中的“左侧没有联动控制流”一致。现场仍需查看左侧控制器的启动
状态或故障指示，现有 CAN 只读数据无法替代该检查。后续用户确认两台左侧
控制器均显示正常绿色指示灯。主机当前只有 `can_left`、`can_right` 两个 CAN
接口，没有遗漏的第三条 CAN；`can_left` 仍由映射文件指定的 USB 序列号和
`gs_usb` 驱动管理。绿色指示灯不能单独证明该控制器正在发送 CAN 帧。
