# 两 CAN 总线完整性排查

## 1. 结论摘要（2026-09-30 实测）

在**四台臂都通电、六关节全部失能、上位机不发送任何帧**的条件下测量两条总线：

| 总线 | 普通帧 | 估算负载 | 共享 ID | CAN 错误帧 |
| --- | ---: | ---: | ---: | --- |
| `can_left` | 6181/s | 686～834 kbit/s（1 Mbit/s 的 69%～83%） | 12 个 | 60 s 窗口实测 586 个（9.77/s），另一次 60 s 实测 0 个 |
| `can_right` | 6181/s | 686～834 kbit/s（69%～83%） | 20 个 | 8 s/20 s 窗口实测约 283/s 与 665/s，另一次 60 s 实测 0 个 |

三条结论：

1. **负载没有余量。** 两 CAN 拓扑把两台臂塞进一条总线，光是臂自己的反馈就占到 69%～83%；
   我们自己的控制流（200 Hz × 5 帧 ≈ 1000 帧/秒）还要再加约 135 kbit/s（+13%），
   最坏情况会顶到约 96%。总线接近饱和时，任何电气余量不足都会被放大成错误帧与延迟。
2. **共享 ID 无法通过配置消除。** 每条总线上有 12（左）／20（右）个 ID 同时被两台设备
   发送：`0x251`～`0x256` 各约 400 Hz、`0x261`～`0x266` 各约 80 Hz（右侧还有未偏移的
   `0x2A1`～`0x2A8` 各约 400 Hz）。固件的驱动反馈族不随 `0x20` 偏移搬移（14.7 已确认），
   所以只能靠**物理分开**解决。
3. **错误帧是间歇的，不是常数。** 同一条总线在不同时刻分别测到 0/s、~10/s、~283/s、
   ~665/s。这更像"边缘条件下的偶发"，而不是某个确定的软件缺陷；因此每次测量都必须
   记录条件，并用 60 s 以上的窗口判读。

另外两条工具层面的实测结论，排查时不要踩：

- **错误帧只交付给显式打开 `CAN_RAW_ERR_FILTER` 的套接字。** 本机 can-utils 2020.11 的
  `candump -e` 在同样条件下报 0 个错误帧（实测 49441 行普通帧、0 行错误帧），而
  `piper_can_quality`（python-can 自动打开该过滤器）和裸套接字都能看到。**基线统计请用
  `piper_can_quality`，不要用 `candump -e` 下结论。**
- 两个适配器都是 candleLight（USB `1d50:606f`），都挂在 **Bus 01** 上，链路各自协商为
  **12 Mbit/s 全速**（`lsusb -t` 显示 `12M`）。全速是 candleLight 的正常形态，不是故障；
  但两台设备共享同一个上游控制器，排查时要把"换口/换线"作为变量之一。

## 2. 负载构成

左总线（`can_left`，主臂已偏移 `0x20`）：

| 帧族 | 实测帧率 | 是否共享 ID | 说明 |
| --- | ---: | --- | --- |
| `0x1C0`～`0x1C3`、`0x212`（末端/手） | 101/s | 否 | Revo2 反馈，20/40 Hz |
| `0x251`～`0x256` 高速关节反馈 | 2400/s | **是**（2×200 Hz） | 每台臂各 200 Hz |
| `0x261`～`0x266` 低速驱动反馈 | 480/s | **是**（2×40 Hz） | 使能位来源 |
| `0x2A1`～`0x2A8` 从臂高速反馈 | 1600/s | 否 | 8 个 ID × 200 Hz |
| `0x2C1`～`0x2C8` 主臂高速反馈 | 1600/s | 否 | 偏移 0x20 后的主臂反馈 |

右总线（`can_right`，**尚未配置偏移**）：`0x2A1`～`0x2A8` 变成 3200/s（两台各 200 Hz），
即从臂反馈族本身也成了共享 ID，共享 ID 总数 20 个。

单台臂一条总线时，同样的组成会降到约 3140 帧/秒（约 350～430 kbit/s，35%～43%），
再叠加我们的控制流仍在 50% 上下，才是有余量的形态。

## 3. 机制

处于"两台设备发同一个 CAN 帧 ID"的状态时：两帧的仲裁 ID 相同，仲裁阶段分不出胜负，
进入数据段后只要载荷有一位不同，落后的那台就会检测到位错误并发出错误帧，两帧都被
作废并稍后重传。这就是：

- 为什么**共享 ID 越多，错误帧越多**（`can_right` 20 个共享 ID 时的错误率明显高于
  `can_left` 的 12 个）；
- 为什么**适配器自己的内核计数始终是 0**（`bus-errors`、`error-warn`、`error-pass`、
  `bus-off`、丢帧全为 0）：发出错误帧的是碰撞中的臂，我们只是收报方；
- 为什么负载高会放大它：接近饱和时发送被推迟，两台同 ID 设备"同时起步"的概率上升。

## 4. 工具与命令

```bash
# 单轮体检（默认 20 s）
ros2 run piper piper_can_quality --port can_left --seconds 60

# 连续三轮，看间歇性（每轮一行可对比摘要）
ros2 run piper piper_can_quality --port can_left --seconds 60 --repeat 3
```

输出包含：分组帧率、估算负载（标称/最坏情况）、共享 ID 清单、错误帧总数/平均/单秒峰值/
状态退化帧数、错误类别与 data、以及"错误帧前后 ±300µs 内出现的 ID 相对基线占比的过代表
倍数"（用来判断是哪些流量在冲突）。

测量前请记录条件：哪几台臂通电、六关节使能状态、是否有人进入示教、主机上有哪些
Piper/ROS 进程、刚做了什么（插拔、上电、改线）。

## 5. 排查步骤（每步都写明判读标准）

**步骤 1：基线。** 四台臂通电、全部失能、无任何控制进程，两条总线各测 3 × 60 s。

- 判读：记录错误率范围。目前已知它会在 0/s 与数百/s 之间波动，所以只测一次没有意义。

**步骤 2：单臂隔离（决定性实验）。** 把 `follower_left` 断电（只留 `master_left` 在
`can_left` 上），再测 `can_left`。

- 判读：
  - 共享 ID 应从 12 个降到 0（`0x251`～`0x256` 从 400 Hz 降到 200 Hz、`0x261`～`0x266`
    从 80 Hz 降到 40 Hz），负载降到约 43%；
  - **错误帧应降到 0**。若错误帧仍然出现，说明当前错误不是"同 ID 碰撞"造成的，而是
    电气/适配器/线缆问题（终端电阻、支线、屏蔽、供电、USB 链路），按步骤 4 的方向查；
  - 若错误帧降到 0，则同 ID 碰撞就是主因，处置见第 6 节 A/B。

**步骤 3：换另一台单臂。** 断电 `master_left`、给 `follower_left` 上电，重复步骤 2。

- 判读：与步骤 2 相同。两次结果不一致时，问题更可能在**那一台臂或它的支线**上。

**步骤 4：适配器与链路互换。** 把左右两个适配器对调（或换 USB 口/换 USB 线），再测。

- 判读：错误跟着**适配器**走 → 查那个适配器；跟着**总线/臂**走 → 查线缆与臂；
  两边都变了 → 查公共因素（供电、接地、主机 USB 控制器）。

**步骤 5：物理检查清单**（每条都做成一次"改前/改后各测 60 s"的对照）：

- 主干两端各一个 **120 Ω 终端电阻**（两条总线都要；总线只在两端有终端，中间设备不接）；
- 支线（stub）尽量短（1 Mbit/s 下建议 ≤ 0.3 m），CANH/CANL 走**双绞**、不要与电机动力线
  并行走线；
- 所有节点**共地**，屏蔽层**单端接地**；
- 臂与适配器的供电是否稳定（示波器/万用表看 24 V 在使能瞬间是否跌落）；
- USB：换口、换线、避开与相机同一 hub；观察 `lsusb -t` 的 `12M/480M` 与 `dmesg` 有无
  USB 复位/溢出；
- 重复步骤 1 的基线测量，并记录每条改动各自的增量效果。

**步骤 6：带控制流复测。** 物理层改动完成后，用 `piper_two_can_align` 的静止目标发帧探针
（`--send --workspace-clear`，它只发从臂标准地址、且先在起点冻结 0.5 s）验证"加入控制流
后错误率是否仍然可控"，再进入阶段 D。

## 6. 处置选项

**A. 一台臂一条总线（推荐）。** 需要**再买两个 USB-CAN 适配器**（现有两个是 candleLight
`1d50:606f`）。收益：共享 ID 归零、每条总线负载降到 35%～43%、主臂与从臂在电气上互不
影响（主臂那侧的扰动不会打断从臂的指令流）。软件侧：直接 SocketCAN 的控制环本来就不经过
ROS 话题，改成"读一条总线、写另一条总线"是小改动，并且可以与固件直连方案共存。

**B. 保持两条总线，降低负载。** 两条路同时走：
- 向厂商确认 `0x251`～`0x256` 与 `0x261`～`0x266` 能否降频或关闭其中一族（这是唯一能真正
  减少共享流量的办法）；
- 软件侧压缩我们自己的控制流：把每周期 5 帧（`0x151` + `0x155`～`0x157` + `0x159`）压到
  3 帧（模式帧只在进入/切换时发、夹爪只在目标变化时发），并把命令频率从 200 Hz 降到
  100 Hz，可省约 9% 负载。
  即使这样仍有 12/20 个共享 ID，**只能减轻，不能消除**。

**C. 维持现状 + 放开错误帧策略（软件侧已生效）。** 只有在物理层确认"错误帧不会引起状态
退化、也不影响跟踪质量"时才可接受：要求 `状态退化帧 = 0`、60 min 连续运行的平均错误率
稳定、跟踪误差无异常。这一条必须与 A 或 B 并行推进，不能单独作为长期方案。

## 8. 与软件门禁的关系

`piper_two_can_teleop` / `piper_two_can_align` / `piper_two_can_identity` 默认使用
`recoverable` 错误帧策略（2026-09-30 决定）：容忍孤立错误帧，只在**状态退化**
（bus-off、错误被动、总线错误）或**持续速率超限**（默认 5 s 窗口平均 > 20 Hz）时中止。
需要回到最严口径时加 `--error-policy strict`。

也就是说：物理层没有弄好之前，软件不会再因为偶发错误帧拒绝启动，但会持续把错误率写进
`/teleop/state` 与 `/diagnostics`；物理层的验收目标是让这些计数长期稳定在 0 附近。
