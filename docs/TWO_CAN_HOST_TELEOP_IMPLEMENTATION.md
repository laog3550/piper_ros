# 两路 CAN 上位机主从摇操实现方案

> **历史方案，已停用。** 当前采用[官方 `0xFA/0xFC` 固件直连方案](OFFICIAL_NATIVE_TELEOP.md)。
> 本文的命令、ROS 服务和自动回位流程不适用于当前 `piper_two_can_teleop` 入口。

> **历史执行口径（2026-10-04）：** 使用 `0xFC + 0x20` 的两 CAN 直接控制。
> 默认可恢复错误策略，自动对齐粗差上限 `30°`、峰值 `5°/s`。
> 左侧自动对齐及 `50 Hz`、30 秒关节跟随已完成真机试验；固定姿态回位已通过。
> ACTIVE 阶段保留跟踪误差观测，取消按误差阈值停流；对齐和回位的误差门禁保留。
> ACTIVE 阶段主臂目标超出从臂可指令范围时钳制输入并继续跟随，仍报告触限位关节。
> 最新进度见第 18 节；右侧六关节 `50 Hz`、30 秒跟随已完成，`200 Hz` 与夹爪仍待验收。
> 流程技术实现见[两 CAN 主从臂遥操作历史资料](TWO_CAN_TELEOP_WORKFLOW.md)。
> 第 14 节保留现场历史，其旧门禁和推断不作为当前启动条件。

## 1. 文档目的

本文定义 PiPER 双侧主从摇操在 Ubuntu/ROS 2 环境下的实现方案。系统只使用两个
SocketCAN 接口，每侧主臂和从臂连接同一条物理 CAN：

```text
can_left
├── 左主臂
└── 左从臂

can_right
├── 右主臂
└── 右从臂
```

当前实现通过官方协议的 CAN ID 偏移区分主从臂，上位机读取主臂位置并向从臂发送目标
位置。[总线完整性文档第 15 节](CAN_BUS_INTEGRITY.md#15-官方角色非对称与双-can-改进方案2026-10-10)
另行定义待验证的 `0xFA + linkage_offset=0x20` 双 CAN 改进方案；它利用
官方示教输入臂只发送控制目标的特性，消除两台 `0xFC` 在低速反馈 ID 上的冲突，同时
保留上位机停止转发后执行固定目标回位的能力。

本文的目标是：

- 左右两对主从臂只占用 `can_left`、`can_right` 两个 CAN 接口；
- 主臂可使用实体示教按钮进入重力补偿；
- 上位机能够分别读取同一 CAN 上的主臂和从臂位置；
- 从臂只响应上位机控制，主臂不响应从臂的标准控制帧；
- 能通过软件明确进入和退出摇操；
- 退出后主从臂全部失能，同时保留主臂 CAN ID 偏移配置；
- 控制环不经过 ROS 话题转发，降低四 CAN 方案中观察到的主机转发延迟。

## 2. 方案结论

### 2.1 运行角色

每台主臂一次性配置为：

```text
linkage_config = 0xFC
feedback_offset = 0x20
ctrl_offset = 0x20
linkage_offset = 0x00
```

每台从臂保持出厂默认配置：

```text
linkage_config = 0xFC
feedback_offset = 0x00
ctrl_offset = 0x00
linkage_offset = 0x00
```

这是当前已部署配置。主臂保持运动输出臂角色 `0xFC`，仅用实体示教按钮进入物理示教/
重力补偿。日常运行程序不发送 `0x470`，避免在主从臂同时在线时广播改写两台臂的角色
和偏移。

先前文档曾断言 `0xFA` 会周期广播 `0x471` 使能帧；现有保存日志只记录到管理器主动
发送的 `0x471`，没有保留能够证明该断言的隔离主臂原始采样。官方资料反而明确说明
`0xFA` 主臂只发送 `0x151`、`0x155`～`0x157`、`0x159` 五类控制帧。因此该断言降级为
待实机核验项，不能再作为排除官方主从角色方案的既定事实。

### 2.2 同一 CAN 上的地址空间

| 功能 | 从臂默认地址 | 主臂偏移 `0x20` 后的地址 |
| --- | --- | --- |
| 运动控制指令 1 | `0x150` | `0x170` |
| 运动控制指令 2 | `0x151` | `0x171` |
| 关节控制 | `0x155`～`0x157` | `0x175`～`0x177` |
| 夹爪控制 | `0x159` | `0x179` |
| 高速状态和运动反馈 | `0x2A1`～`0x2A8` | `0x2C1`～`0x2C8` |

Ubuntu 上位机按 CAN ID 路由数据：

```text
0x2Ax → 从臂反馈缓存
0x2Cx → 主臂反馈缓存
0x15x → 只控制从臂
0x17x → 只控制主臂
```

左侧现场已经验证：

- `feedback_offset=0x20` 后，主臂 `0x2A1`～`0x2A8` 消失，`0x2C1`～`0x2C8`
  各以约 `200 Hz` 上报；
- 主臂重启后偏移仍然保存；
- 主臂忽略标准 `0x151`；
- 主臂接受偏移后的 `0x171`；
- 用 `0x171` 切换到 CAN 控制模式并恢复待机的过程中，六关节实测位移均为
  `0.0000°`。

### 2.3 不能被偏移解决的广播和冲突

以下内容不能按主从臂单独寻址：

- `0x470` 主从角色和地址偏移配置帧是广播帧；
- `0x471` 电机使能/失能帧是广播帧；
- 左侧实测 `0xFC + feedback_offset=0x20` 只移动了 `0x2A1`～`0x2A8` 高速反馈，
  `0x251`～`0x266` 低速驱动反馈仍使用默认 ID。

因此，本方案将同一侧两台臂作为一个使能域：

```text
进入时：同侧两台臂一起使能
退出时：同侧两台臂一起失能
```

程序不能宣称能够从共享总线的 `0x261`～`0x266` 中识别某一帧来自主臂还是从臂。
验证整侧使能/失能时，应检查观察窗口内所有状态样本是否一致；出现使能和失能样本混合时，
判定为 `PARTIAL`，禁止进入摇操。

## 3. 与官方 Windows 上位机的关系

官方 ArmRobotTool 的“联动控制”界面提供以下字段：

- 联动设置指令；
- 地址偏移值；
- 反馈指令偏移值；
- 控制指令偏移值。

它使用的底层协议与官方 SDK 的 `MasterSlaveConfig()` 相同。Windows 并不依赖 USB-CAN
序列号区分同一总线上的两台臂，而是解析不同的 CAN ID 窗口。Ubuntu 实现不需要复刻
Windows 图形界面，只需要实现相同的偏移解码和路由规则。

官方文档还说明，主臂角色在上位机左上角可能显示“离线”或红绿闪烁，但联动反馈仍可显示
“主臂”。这是主臂角色拒绝普通控制的表现，不等同于 CAN 物理掉线。

## 4. 一次性离线配置

### 4.1 配置约束

`0x470` 没有设备地址。配置某一台主臂时，同侧从臂必须断电或断开 CAN。不得在两台臂
同时在线时发送主臂偏移配置，否则两台臂会得到相同地址空间。

一次性配置按左右两侧分别执行。

### 4.2 左主臂配置

1. 左从臂断电，只保留左主臂连接 `can_left`。
2. 只读确认高速反馈约为单臂帧率，且没有控制指令帧。
3. 发送以下配置：

   ```bash
   ros2 run piper piper_master_slave \
     --output-arm \
     --feedback-offset 0x20 \
     --ctrl-offset 0x20 \
     --linkage-offset 0x00 \
     --port can_left \
     --isolated-master --send
   ```

4. 左主臂断电重上电。
5. 只读确认：
   - `0x2A1`～`0x2A8` 为 `0 Hz`；
   - `0x2C1`～`0x2C8` 各约 `200 Hz`；
   - 没有 `0x15x` 或 `0x17x` 主动控制流；
   - CAN 无错误和丢帧。
6. 给左从臂上电，确认同一 CAN 上同时存在一套 `0x2Ax` 和一套 `0x2Cx`。

### 4.3 右主臂配置

右侧步骤相同，将接口替换为 `can_right`。

### 4.4 严禁使用的日常命令

配置完成后，日常停止流程不得执行：

```bash
ros2 run piper piper_master_slave --output-arm --send
```

该命令默认发送：

```text
0x470 FC 00 00 00 00 00 00 00
```

它会把 `feedback_offset` 和 `ctrl_offset` 清零。两台臂在线时，两台都会收到清零帧，
随后重新在 `0x2Ax/0x15x` 上发生冲突。

运行程序不得提供自动发送 `0x470` 的路径。角色和偏移只能通过独立维护命令离线配置。

## 5. Ubuntu 控制程序设计

### 5.1 进程结构

每侧运行一个直接 SocketCAN 控制进程：

```text
piper_two_can_teleop --side left  --port can_left
piper_two_can_teleop --side right --port can_right
```

控制进程内部直接完成：

```text
接收主臂 0x2Cx
→ 解码最新六关节和夹爪位置
→ 安全门禁、对齐和限幅
→ 编码从臂 0x151/0x155～0x157/0x159
→ 发送到同一个 SocketCAN 接口
```

实时控制环不得经过：

```text
SDK 接收节点 → ROS JointState → teleop 节点 → ROS JointState → SDK 控制节点
```

ROS 2 只用于启停服务、状态发布和诊断，不进入每帧运动数据路径。

### 5.2 建议新增模块

| 文件 | 责任 |
| --- | --- |
| `piper_two_can_teleop.py` | 单侧直接 CAN 控制环和状态机 |
| `piper_two_can_manager.py` | 左右两侧统一启停、联锁和 CLI |
| `piper_two_can_identity.py` | 只读确认同侧主从臂地址身份和反馈频率门禁 |
| `piper_two_can_align.py` | 共总线下单侧 minimum-jerk 自动对齐和运行时安全门禁 |
| `start_two_can_teleop.launch.py` | 启动左右控制进程和诊断 |
| `test_piper_two_can_teleop.py` | `vcan` 协议、状态机和故障测试 |

可复用现有实现：

| 现有模块 | 可复用内容 |
| --- | --- |
| `piper_feedback.py` | 单位换算、限位、滤波、最小加加速度对齐 |
| `piper_master_state.py` | `0x20` 偏移反馈解码 |
| `piper_two_can_teleop.py` | 直接 CAN 会话、对齐衔接与滤波限速 |
| `piper_arm_enable.py` | `0x471` 整侧使能/失能载荷和读回逻辑 |

| `piper_bus_probe.py` | 总线帧率、控制流和错误诊断框架 |

旧的 `piper_teleop.py`、`piper_teleop_fast.py` 和配套 ROS 转发启动入口已删除。

上表各模块的落地状态、命令行用法、ROS 接口和验证结果见第 15 节。

### 5.3 SocketCAN 过滤

左、右进程只打开各自接口，并至少接收：

```text
主臂：0x2C1～0x2C8
从臂：0x2A1～0x2A8
共享低速状态：0x251～0x266
配置/使能观察：0x470、0x471
标准控制观察：0x150～0x15F
偏移控制观察：0x170～0x17F
```

运行时应关闭本机发送回环或明确标记本机帧，避免把自己的控制流误判为外部控制器。
发现同一总线上存在未知 `0x15x` 发送源时，进入故障锁存，禁止多控制器竞争。

### 5.4 六关节快照

六关节位置来自三帧：

```text
主臂：0x2C5、0x2C6、0x2C7
从臂：0x2A5、0x2A6、0x2A7
```

程序只在三帧均更新且时间跨度不超过阈值时生成快照。建议初始参数：

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `joint_stale_timeout_ms` | `30` | 任一关节对超过该时间即过期 |
| `snapshot_max_skew_ms` | `10` | 三个关节对允许的最大时间差 |
| `master_min_hz` | `150` | 主臂每个高速反馈 ID 的最低频率 |
| `follower_min_hz` | `150` | 从臂每个高速反馈 ID 的最低频率 |
| `command_rate_hz` | `200` | 上位机最大发送频率 |

收到主臂 `0x2C7` 后，如三帧均新鲜，可立即生成并发送一组从臂关节目标，避免等待固定
ROS 定时器。控制进程始终使用最新值，不积压历史目标。

### 5.5 单位和编码

| 数据 | CAN 原始单位 | 程序内部单位 |
| --- | --- | --- |
| 关节角 | `0.001 degree`，有符号 32 位大端 | `rad` |
| 夹爪开口 | `0.001 mm`，有符号 32 位大端 | `m` |
| 夹爪力矩 | `0.001 N·m` | `N·m` |

控制帧编码必须复用官方 SDK 的字段定义和限位规则。不得使用现有代码中的近似角度换算
系数，统一使用 `pi / 180`。

## 6. 状态机

每侧独立维护状态；双侧管理器只在两侧均满足门禁时允许同步启动。

| 状态 | 含义 | 允许发送的帧 |
| --- | --- | --- |
| `OFFLINE` | 任一必要反馈窗口不存在 | 无 |
| `IDLE_DISABLED` | 两套反馈正常，整侧失能 | 无运动帧 |
| `ARMING` | 正在整侧使能并验证 | 一帧 `0x471 07 02` |
| `WAIT_TEACH` | 等待主臂进入实体示教/重力补偿 | 无运动帧 |
| `ALIGNING` | 从臂以受限轨迹对齐主臂 | 标准 `0x15x` |
| `ACTIVE` | 实时摇操 | 标准 `0x15x` |
| `RETURNING` | 按启动时冻结的从臂起点回位 | 标准 `0x15x` |
| `WAIT_TEACH_RELEASE` | 回位成功，等待新的实体示教释放确认 | 从臂待机帧；禁止关节目标 |
| `STOPPING` | 操作员已确认实体示教关闭，正在失能并验证 | `0x471` |
| `FAULT_LATCHED` | 超时、取消、混合使能、外部控制或 CAN 故障 | 仅尽力停止，不自动失能 |

任何故障锁存后，不得因为数据自动恢复而直接回到 `ACTIVE`。须人工处理并重启会话，重新通过门禁。

## 7. 进入摇操流程

### 7.1 前置检查

每侧必须同时满足：

1. `0x2A1`～`0x2A8` 各约 `200 Hz`；
2. `0x2C1`～`0x2C8` 各约 `200 Hz`；
3. 不允许 `0x2Ax` 或 `0x2Cx` 出现约 `400 Hz`；出现 `400 Hz` 表示两台臂地址冲突；
4. 没有外部 `0x15x` 或 `0x17x` 控制流；
5. CAN 为 `ERROR-ACTIVE`，无持续错误、丢帧或 bus-off；
6. 共享低速使能状态一致为失能；
7. 主从关节位置有效且在允许范围内。

可先用只读身份确认命令执行第 1～4 项中的地址和控制流检查：

```bash
ros2 run piper piper_two_can_identity --side left --port can_left
ros2 run piper piper_two_can_identity --side right --port can_right
```

命令逐项统计 `0x2A1`～`0x2A8` 和 `0x2C1`～`0x2C8` 的帧率。只有两套窗口
全部达到 `150 Hz`、均未达到地址冲突阈值 `300 Hz`，并且观察期间没有
`0x15x`、`0x17x`、`0x470`、`0x471`，CAN 错误未触发第 15.4 节策略，且主臂 `0x2C1` 未报告
`0x06` 联动示教输入模式时才返回成功。该命令只接收，
不会发送配置、使能、失能或运动帧。它确认的是 CAN 地址身份；实体主臂必须已经按第 4 节
的隔离流程完成离线配置，不能仅凭共享的 `0x251`～`0x266` 低速反馈反推实体身份。

### 7.2 启动顺序

```text
IDLE_DISABLED
→ 广播 0x471 07 02，使同侧主从臂一起使能
→ 验证低速状态窗口内所有样本均为 enabled
→ 操作员按主臂实体示教按钮，进入重力补偿
→ 验证主臂 0x2Cx 持续更新
→ 计算主从关节差
→ 受限对齐
→ ACTIVE
```

进入前必须设置关节差门禁。建议：

| 项目 | 建议初值 |
| --- | ---: |
| 自动对齐粗差防呆上限 | `30°` |
| 超过该值 | 拒绝启动，要求人工摆近 |
| 自动对齐时间 | 不少于 `2 s`，按最大差和速度限制延长 |
| 对齐轨迹 | minimum-jerk |

自动对齐时主臂应保持稳定；主臂移动超过阈值时重新规划或取消启动。

### 7.3 两 CAN 自动对齐工具

阶段 D 使用 `piper_two_can_align`，不再调用依赖四路 ROS 话题和四个控制节点的旧
`piper_teleop.py`。新工具直接在单侧共享接口上读取主臂 `0x2C5`～`0x2C7` 和从臂
`0x2A5`～`0x2A7`，只向从臂标准地址发送 `0x151`、`0x155`～`0x157`。

先执行默认干跑：

```bash
ros2 run piper piper_two_can_align --side left --port can_left
```

干跑会执行身份、控制冲突、快照时效、关节限位和 `30°` 粗差防呆门禁，打印
minimum-jerk 轨迹的时长与峰值速度，但不发送任何帧。默认参数为：最短 `2 s`、峰值不超过
`5°/s`、控制频率 `50 Hz`、`MotionCtrl_2` 速度百分比 `5%`。实际时长由最大位移自动延长，
而不是要求操作员先手动摆到精确角度。

真正发送前必须由外部流程完成以下操作：

1. 确认人员和线缆退出运动空间；
2. 用一帧 `0x471 07 02 ...` 整侧使能并完成读回；
3. 操作员通过实体按键让主臂进入示教模式并明确确认；
4. 保持主臂稳定，再执行：

```bash
ros2 run piper piper_two_can_align --side left --port can_left \
  --send --workspace-clear
```

发送模式会再次运行完整门禁；只有预检窗口内六关节每个低速样本都为 enabled 才允许运动。
通过门禁后先以正式运行的 `50 Hz` 频率持续 `0.5 s` 发送冻结在从臂起点的静止目标，并再
留出 `0.1 s` 无发送观察窗；只有该探针期间同样没有 CAN 错误、失能、主臂漂移或从臂偏移，
才开始改变目标。错误帧按第 15.4 节策略处理，不要求计数为零。该探针用于发现“只读时正常、加入控制流后才出现”的共享总线冲突，不表示
总线冲突已被软件修复。
运行中发现反馈超时、三帧时间跨度过大、主臂漂移、从臂跟踪误差、任一关节失能、外部
`0x15x/0x17x` 控制流、`0x470` 或 `0x471` 时立即中止。完成或中止后只发送从臂标准待机帧，
不会发送 `0x170`、`0x171` 或 `0x471`；实体示教退出和整侧失能仍按 8.1 的人工确认流程
执行。

从臂起点超出自身指令范围时仍直接拒绝。主臂目标仅轻微越界时，工具会把对齐目标限制到
从臂最近可达角度并明确打印“主臂读数 → 对齐目标”；默认允许的单关节钳制量不超过 `1°`，
超过仍拒绝，以防错误反馈被当成合法目标。限幅后的位移同样受 `30°` 粗差上限和 `5°/s`
峰值速度约束。

## 8. 退出摇操流程

### 8.1 正常停止

**最终方案决策（2026-09-30）：** 实体示教模式只由操作员通过主臂实体按钮进入和退出；
上位机不得用 `0x170` 或 `0x171` 代替实体按键。上位机负责立即停止运动流、等待操作员
显式确认、发送 `0x471` 整侧失能并完成读回验证。

```text
ACTIVE
→ 停止接收新的摇操请求
→ 停止实时关节目标流
→ 从臂切回待机
→ RETURNING（固定目标为启动请求通过门禁后、使能前冻结的从臂起点）
→ 回位与到位核对成功
→ WAIT_TEACH_RELEASE（清除旧确认，开放新窗口）
→ 提示操作员关闭主臂实体示教按钮
→ 操作员确认实体示教按钮已关闭
→ 重新取得新鲜快照并核对起点
→ 广播失能
→ 验证观察窗口内全部关节状态均为 disabled
→ IDLE_DISABLED
```

建议帧序列：

```text
从臂待机：0x151 00 01 01 00 00 00 00 00
整侧失能：0x471 07 01 00 00 00 00 00 00
```

其中：

- `0x151` 只应被默认控制地址的从臂接受；
- `0x170 00 00 02 00 00 00 00 00` 的第 2 字节是
  `grag_teach_ctrl=0x02`，只结束通过协议启动的拖动示教记录。左侧现场实测表明它不能退出
  实体按钮产生的 `0x02` 示教模式，因此不得用于该停止流程；
- **严禁把 `0x170 02 00 00 00 00 00 00 00` 用作正常退出。** 该帧的第 0 字节是
  `emergency_stop=0x02`，官方 SDK 定义为急停恢复，并由 `ResetPiper()` 使用；它不是退出
  示教指令，现场已观测到发送后多关节大幅位移；
- `0x171` 虽能切换主臂控制模式，但正常停止不需要再向主臂发送控制模式帧；实体按钮的
  进入和退出都由操作员完成，上位机只负责停从臂目标流与整侧失能；
- `0x471` 会同时失能两台臂。

退出先停止跟随，在同一会话内完成固定目标回位，再进入 `WAIT_TEACH_RELEASE`。
该等待状态不再发送 `0x155`～`0x159`。操作员关闭实体示教按钮并作新的明确确认后，
上位机重新核对起点并发送 `0x471`。现场实测中，操作员手动退出实体
示教且六关节已经 disabled 后，`0x2C1` 仍持续报告 `0x02`；因此该字段不能证明实体按钮
当前处于开启还是关闭状态，`teach_released` 的操作员确认是正常停止的必要输入。程序不能
等待 `0x2C1=0x00`，也不能自行发送 `0x170` 或 `0x171` 代替实体按键操作。

失能读回必须检查观察窗口内所有低速状态样本；出现 enabled/disabled 混合时继续等待或
判为 `PARTIAL`，不能仅凭最后一个样本成功。整个退出窗口仍须执行位移门禁。

### 8.2 故障停止

反馈超时、对齐或回位误差超限、控制源竞争或错误策略触发后，立即停止关节和夹爪目标流，
发送从臂待机并保持 `FAULT_LATCHED`，不自动回位或发送常规失能帧。实体示教退出和故障恢复由人处理；故障原因始终保留，不能自动恢复。

程序默认不发送未经现场验收的急停或重置载荷；可选 `--fault-fast-stop` 仅向从臂发送
`0x150 01 ...`。没有主臂 `0x170/0x171` 控制路径。软件退出不能替代物理急停。

## 9. ROS 2 接口

建议接口如下：

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `/teleop/left/start` | `std_srvs/srv/Trigger` | 请求左侧进入摇操 |
| `/teleop/left/teach_engaged` | `std_srvs/srv/Trigger` | 操作员确认左主臂已进入实体示教 |
| `/teleop/left/stop` | `std_srvs/srv/Trigger` | 左侧停跟随并回位，成功后等待新的释放确认 |
| `/teleop/left/teach_released` | `std_srvs/srv/Trigger` | 操作员确认左主臂实体示教按钮已关闭 |
| `/teleop/right/start` | `std_srvs/srv/Trigger` | 请求右侧进入摇操 |
| `/teleop/right/teach_engaged` | `std_srvs/srv/Trigger` | 操作员确认右主臂已进入实体示教 |
| `/teleop/right/stop` | `std_srvs/srv/Trigger` | 右侧停跟随并回位，成功后等待新的释放确认 |
| `/teleop/right/teach_released` | `std_srvs/srv/Trigger` | 操作员确认右主臂实体示教按钮已关闭 |
| `/teleop/start` | `std_srvs/srv/Trigger` | 两侧联锁启动 |
| `/teleop/stop` | `std_srvs/srv/Trigger` | 两侧停跟随并独立回位，成功后分别等待新的释放确认 |
| `/teleop/state` | 自定义状态消息或诊断 | 当前状态、模式、帧率、误差和故障原因 |
| `/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | CAN 和安全诊断 |

`start` 服务只提交进入请求并进入 `WAIT_TEACH`。由于 `0x2C1=0x02` 可能跨实体按钮操作
残留，只有对应侧处于 `WAIT_TEACH` 时才接受 `teach_engaged` 操作员确认；确认后仍须检查
两臂反馈、位置差和使能门禁，不得直接进入 `ACTIVE`。

`stop` 服务必须立即停止运动流，但它不是“已完成失能”的同步承诺：正常情况下先进入 `RETURNING`，回位核对成功后进入
`WAIT_TEACH_RELEASE`。只有对应侧处于该状态时才接受 `teach_released`；确认后完成
`0x471` 和失能读回。状态接口必须明确发布“等待关闭实体示教”以及
“停止已完成”，双侧停止只有两侧都到达 `IDLE_DISABLED` 才算完成。

进程收到 `SIGINT`、`SIGTERM` 或未捕获异常时，应尝试执行故障停止；但进程崩溃无法保证
软件帧一定发出，现场必须保留物理急停和断电手段。

## 10. 延迟控制

两 CAN 方案仍是上位机桥接，因此不会达到固件直连的理论最低延迟。实现应避免额外的软件
排队：

- 每侧一个直接 CAN 进程；
- 只处理最新关节快照；
- 不在控制环中发布和订阅 `JointState`；
- 不使用可靠 ROS 队列转发运动指令；
- SocketCAN 接收使用内核时间戳；
- 控制线程可配置 CPU affinity 和实时调度，但必须提供无权限时的安全降级；
- 诊断、日志和可视化在非实时线程执行；
- 日志不得逐帧打印；
- 滤波器不得引入不可控的长窗口相位延迟。

验收时分别记录：

```text
主臂反馈接收时间
从臂目标发送时间
从臂反馈开始变化时间
稳定跟踪误差
```

先测 CAN 接收至发送的软件延迟，再测端到端机械响应延迟，不能只用视觉主观判断。

## 11. 安全门禁

以下任一条件出现时禁止进入或立即退出：

- `0x2Ax` 或 `0x2Cx` 缺失；
- 任一高速反馈窗口约为 `400 Hz`，表示地址冲突；
- 任一必要反馈超过新鲜度阈值；
- 同一低速状态 ID 同时出现使能和失能样本；
- 从臂错误位非零；
- 主从位置差超过自动对齐范围；
- 对齐或固定目标回位的轨迹误差、终点误差超限；
- 出现非本进程产生的 `0x15x` 控制帧；
- SocketCAN 进入 `ERROR-PASSIVE` 或 `BUS-OFF`；
- 运行中收到 `0x470`；
- 当前 `0xFC + 0x20` 运行配置发现主臂处于 `0xFA`，或任何运行配置观察到非本进程
  发送的周期 `0x471 07 02`。改进方案实现后，`0xFA` 应由所选输入模式显式允许，
  不能继续沿用当前身份门禁直接放行。

运行时观察到 `0x470` 应直接锁存故障，因为这意味着角色或地址空间可能已经被修改。

## 12. 自动测试

使用两套 `vcan` 分别模拟左右总线，至少覆盖：

1. 同时解析一套 `0x2Ax` 和一套 `0x2Cx`；
2. 两个反馈窗口均为约 `200 Hz` 时允许进入；
3. 任一窗口为约 `400 Hz` 时拒绝进入；
4. `0x2Cx` 主臂目标只编码为从臂 `0x15x`；
5. 控制程序从不发送 `0x17x` 关节目标；
6. 控制程序从不发送 `0x470`；
7. 主臂反馈超时后停止运动流并进入 `FAULT_LATCHED`；
8. 从臂反馈超时后执行故障停止；
9. 低速使能样本混合时判定 `PARTIAL`；
10. 正常停止顺序固定为停流、从臂待机、等待实体示教关闭确认、失能、验证，并断言不发送
    `0x170` 或 `0x171`；
11. 进程重启不能自动进入 `ACTIVE`；
12. 相同时间戳的主臂快照不会重复排队；
13. 关节目标超限时拒绝发送，不允许静默钳位造成意外运动；
14. 左侧进程绝不打开 `can_right`，右侧进程绝不打开 `can_left`。

### 14.1 左侧阶段 C 错误帧实测与纠正

2026-09-30 在左从臂断电、左主臂使用 `FC 20 20 00` 且进入实体示教模式的条件下，曾按
旧方案错误发送 `0x170 02 00 00 00 00 00 00 00`。后续核对官方 SDK 确认该载荷为
`MotionCtrl_1(emergency_stop=0x02, track_ctrl=0, grag_teach_ctrl=0)`，含义是急停恢复/
机械臂重置，不是退出拖动示教。以下结果只用于说明该帧危险，**不得作为正常停止方案复用**：

- 实体示教按钮仍处于开启状态时发送该错误帧，主臂只短暂
  回到 `0x00`，随后恢复 `0x02`；紧接着发送 `0x471 07 01 00 00 00 00 00 00`，
  观察到的 `1191` 个低速状态样本中有 `1185` 个仍为 enabled，失能不能保持；
- 关闭实体示教按钮后，主臂仍保持 `0x02`，再次发送该错误帧后最后 `1 s` 持续为
  `0x00`；随后发送 `0x471` 并观察 `5 s`，`1248` 个低速状态样本全部为 disabled，
  没有自动重新使能、外部控制帧或 CAN 错误；
- 第二次过程中观测到最大关节位移：`j5=7.116°`；再次固定主臂复测错误帧时，退出窗口
  最大位移进一步达到 `j4=16.078°`、`j5=21.223°`、`j6=22.677°`。两次均不满足
  “退出示教且不产生运动”的验收条件；
- `0x471` 的稳定失能读回本身通过，但不能抵消错误恢复帧造成的运动风险。

该实测已证明 `0x170 02 00 00 ...` 不得用于停止流程。复测时必须固定或可靠托稳主臂、
确认发送前姿态稳定，并把模式切换帧前后的短窗口位移门禁纳入判定，不得仅凭模式变为
`0x00` 和失能样本全为 disabled 判定通过。

### 14.2 正确拖动示教字段实测

在主臂固定、发送前 `3 s` 六关节波动均为 `0.0000°` 的条件下，发送
`0x170 00 00 02 00 00 00 00 00`：

- 随后 `2 s` 的 `0x2C1` 共 `400` 帧，全部仍为 `0x02`；
- 退出帧窗口内六关节位移均为 `0.0000°`，说明该帧本身未引起运动，但也没有退出实体
  按钮产生的示教模式；
- 随后发送 `0x471 07 01 ...`，最终六关节能稳定保持 disabled，但 `0x2C1` 仍持续为
  `0x02`；
- 因残留的 `0x02` 可能在下次使能时恢复示教状态，不能把“电机已失能”单独视为正常停止
  完成。

结论：`grag_teach_ctrl=0x02` 不适用于退出实体按钮产生的示教模式，也不应再尝试用
`0x171` 替代操作员按键。正常停止采用操作员确认实体示教已退出后只发送 `0x471` 的方案；
该方案的左侧纯净链路验收结果见 14.4。

### 14.3 实体按键手动退出后的反馈特征

操作员再次按实体示教按钮后，现场确认实体示教可以正常退出；但只读观察仍得到：

- `0x2C1` 连续 `3 s` 共 `600` 帧，全部为 `0x02`；
- 六关节低速状态全部为 disabled；
- 六关节位置在 `3 s` 内波动均为 `0.0000°`；
- 无外部控制帧或 CAN 错误。

因此 `0x2C1=0x02` 在该固件上会残留，不能作为实体按钮当前状态的可靠判据。上位机必须
在进入时保留 `WAIT_TEACH` 和显式 `teach_engaged` 操作员确认，在退出时保留
`WAIT_TEACH_RELEASE` 和显式 `teach_released` 操作员确认；收到退出确认后只执行整侧失能
及读回验证。

### 14.4 左侧纯净退出链路验收

2026-09-30 在左从臂断电、左主臂反馈偏移为 `0x20`、无后台控制进程的条件下，按正式方案
完成验收：

- 起始状态连续观察 `5 s`，六关节全部为 disabled，六关节最大位移均为 `0.000°`；

### 14.11 失能静止状态下的 CAN 错误帧基线

14.7～14.10 把错误帧归因于“整侧使能 + 实体示教 + 下发目标”之后的时序冲突。为确认这一点，
在**没有任何上位机发送、四台臂全部通电且失能、没有任何 Piper/ROS 控制进程**的条件下做了
长时间只读统计（2026-09-30，python-can 只收不发）：

| 观测 | 普通帧 | CAN 错误帧 | 说明 |
| --- | ---: | ---: | --- |
| `can_left` 60 s | 370861（6181/s） | 586（9.77/s） | 分布在 36 个整秒里，每秒 4～47 个 |
| `can_left` 30 s 复测 | 185431 | 12（0.4/s） | 同一状态，速率差 20 倍以上 |
| `can_left` 3 s 门禁窗口 | — | 0 | 只读干跑时的窗口 |
| `can_left` 2 s 窗口 × 3 次 | — | 0 / 0 / 15 | 同一台机器连续三次调用身份门禁 |
| `can_right` 20 s | 136892 | 约 13300（665/s） | 该侧仍未配置，`0x2A1`～`0x2A8` 各约 400 Hz |

同一批数据里还有几点可以确认：

- 错误帧全部 `is_rx=True`，即来自总线，不是本机或套接字自己生成的；
- 错误类别只有 `0x4`（控制器问题）与 `0xC`（控制器问题｜协议违规）两类，与 14.9、14.10
  记录的 ID 相同；
- 接口统计始终为 `ERROR-ACTIVE`，`bus-errors`、`error-warn`、`error-pass`、`bus-off`
  和 RX/TX 丢帧计数全为 0；
- `can_right` 的 ID 分布是“两台臂共用默认反馈族”的未配置状态（`0x2A1`～`0x2A8` 约
  400 Hz），它的错误率是左侧的约 70 倍：目前唯一与错误率同向变化的量就是**同 ID 发送
  者的数量**。

由此可以得到三条对后续决策有影响的结论：

1. **错误帧不需要运动、使能或示教就会出现。** 之前“开始下发目标后才出现错误”的观察
   不能当作因果结论：2 s 的只读窗口在 10 Hz 的基线速率下几乎必然撞上错误帧，而 0.4 Hz
   的窗口又常常干净通过。14.7／14.10 的中止因此更可能是**基线噪声**，不是目标流引入的
   新故障。
2. **共享 ID 冲突仍是目前最符合证据的解释**，只是它的触发条件与使能/示教无关，而是与
   “同一条总线上有几台设备在发同一个 CAN ID”相关。
3. **“任何错误帧都中止”的门禁在真机上无法稳定通过**，它不是软件缺陷，而是物理层／固件
   层面的待解决项：共享 ID 无法通过 `0x470` 偏移消除（14.7 已确认 `0x251`～`0x266`
   不随偏移移动），可选的处置见 15.6。

### 14.12 负载与共享 ID 实测：两 CAN 拓扑没有余量

2026-09-30 用新增的只读工具 `piper_can_quality` 在四台臂通电、六关节全部失能、上位机
不发任何帧的条件下测量两条总线：

| 总线 | 普通帧 | 估算负载（最坏情况） | 共享 ID | 错误帧 |
| --- | ---: | ---: | ---: | --- |
| `can_left` | 6181/s | 686～834 kbit/s（69%～83%） | 12 个 | 两次 60 s 窗口：586 个（9.77/s）与 0 个 |
| `can_right` | 6181/s | 686～834 kbit/s（69%～83%） | 20 个 | 20 s 窗口约 665/s；另一次 60 s 窗口 0 个 |

要点：

- 光是臂自己的反馈就占掉 69%～83% 的带宽。我们加上 200 Hz × 5 帧的控制流
  （约 135 kbit/s，+13%）后，最坏情况会顶到约 96%，**两 CAN 拓扑从一开始就没有余量**。
  这比"同 ID 碰撞"更基础：即使没有碰撞，总线也在饱和边缘。
- 共享 ID 在左侧是 `0x251`～`0x256`（各 400 Hz）与 `0x261`～`0x266`（各 80 Hz），
  右侧还要多一组未偏移的 `0x2A1`～`0x2A8`（各 400 Hz）。固件不随 `0x20` 偏移搬移
  驱动反馈族，所以**只能靠物理分开解决**。
- 错误帧是**间歇**的：同一条总线在不同时刻分别测到 0/s、约 10/s、约 283/s、约 665/s，
  所以单次短窗口测量不能作为判据，必须记录条件并做 60 s 以上窗口的对照。
- 错误帧只交付给显式打开 `CAN_RAW_ERR_FILTER` 的套接字：本机 can-utils 2020.11 的
  `candump -e` 实测报 0 个（49441 行普通帧、0 行错误帧），基线统计必须用
  `piper_can_quality`。

完整的物理层排查步骤（单臂隔离的决定性实验、适配器互换、终端电阻/支线/共地/供电清单）
与处置选项写在 **`docs/CAN_BUS_INTEGRITY.md`**。

### 15.2 单侧命令行用法

只读干跑（默认，不发送任何帧）：

```bash
ros2 run piper piper_two_can_teleop --side left --port can_left
```

输出包括身份门禁结果、六关节使能样本、CAN 错误帧统计、两侧夹爪开口，以及当前姿态下的
minimum-jerk 对齐计划。它只读，可以在任何时候运行。

真正运行（必须显式确认工作空间已清空）：

```bash
ros2 run piper piper_two_can_teleop --side left --port can_left \
  --send --workspace-clear
```

运行过程与操作员交互：

```text
只读门禁（默认 2 s）
→ 按回车提交启动请求
→ 程序广播一帧 0x471 07 02 并读回验证整侧使能
→ 提示“用主臂实体按钮进入示教并托稳”，按回车确认
→ 受限对齐（默认最短 2 s、峰值 5°/s、速度百分比 5%）
→ 进入实时跟随（默认 200 Hz、速度百分比 100）
→ Ctrl-C：立即停止目标流 + 从臂切回待机
→ 提示“关闭实体示教按钮后按回车”，确认后广播 0x471 07 01 并读回失能
```

没有给出实体示教退出的确认时，程序**不会发送失能帧**（主臂会失去重力补偿），而是打印
人工失能与断电的指引；退出码为 `4`。故障（反馈超时、外部控制帧、CAN 错误帧、对齐
或回位误差超限、失能读回失败……）一律走故障停止并锁存，本进程不再自动进入摇操。

`piper_two_can_align` 保持独立可用（阶段 D 的单步对齐验收），语义与 7.3 相同。

管理器收到 Ctrl-C 或 SIGTERM 时按“只停流、不失能”处理，并提示用
`ros2 run piper piper_arm_enable --disable --send` 完成人工失能。

### 15.4 CAN 错误帧策略

**2026-09-30 决定：默认改为 `recoverable`。** 14.11 的实测说明 `strict`
（任何错误帧都中止）在两台臂同总线时无法稳定通过——它会把总线基线的偶发错误帧当成启动
失败。现在三个工具（identity／align／teleop，以及管理器）默认都用 `recoverable`，
语义是：

```bash
--error-policy recoverable --max-error-rate-hz 20
```

它的语义是：

- 控制器状态退化（`bus-off`、错误被动、总线错误类别）**永远**直接中止，两种策略一致；
- `recoverable` 下，孤立的、能被 CAN 自动重传恢复的错误帧只计数并写进状态与诊断，
  速率超过上限（默认 20 Hz）才中止；
- 速率上限按**持续窗口内的平均速率**判定（默认 5 s 窗口、20 Hz），而不是单秒峰值：
实测错误帧是突发的，单秒最高见过 47 个，用峰值会把正常突发误判成故障。

需要回到最严口径时，所有工具都支持 `--error-policy strict`。物理层未完成的阶段，
`recoverable` 只是让软件不再被偶发错误帧拦住；物理层的验收目标仍是让
`/teleop/state` 与 `/diagnostics` 里的错误计数长期稳定在 0 附近（见
`docs/CAN_BUS_INTEGRITY.md`）。

六关节初始样本均为 disabled。两只从臂 j2 反馈分别为 `-2.066°`、`-2.017°`，
略低于 `-2.000°` 指令下限。摇操启动规划现仅容许 `0.1°` 内的起点偏差，
首个指令投影到限位边界；独立对齐工具仍按原规则拒绝任何起点越界。

操作员确认两侧运动空间清空、机械臂托稳和实体示教初始关闭后，管理器完成
整侧使能读回。两侧实体示教确认后，对齐最大位移左 `21.853°`、右 `9.951°`，
夹爪随对齐目标左 `17.25 mm`、右 `17.40 mm`。两侧随后同步以 `50 Hz`
运行满 `30 s`，按时停止目标流并切回从臂待机；周期日志中两侧主从臂反馈
约 `200 Hz`，夹爪指令在运行中覆盖 `0～80 mm`。左侧累计 `11` 个 CAN
错误帧，右侧为 0，均未触发故障；这不能代替持续运行的总线稳定性验收。

操作员确认两侧实体示教已退出后，管理器发送整侧失能，完整读回窗口内所有
低速样本均为 disabled，双侧会话最终为 `IDLE_DISABLED`、退出码 0。
管理器退出后的独立 `2 s` 只读复核再次确认两侧身份为 `CONFIRMED`、
使能样本全部 disabled、错误帧为 0。此次未执行从臂返回本轮起点；
失能后的夹爪开口读数左 `0.4 mm`、右 `0.2 mm`，没有在 ACTIVE 阶段独立
记录夹爪实际轨迹，因此尚不能据此确认动态开合比例。

### 18.8 正常退出前自动回位与原位核对（2026-10-06）

第 18.7 节测试在失能前漏做从臂回位，失能后两侧六关节均已偏离本轮起点。
后续正常退出改为：停流待机 → 操作员确认两侧主臂实体示教已关闭 →
从臂六关节与夹爪自动返回各自本轮起点 → 重新采样核对 → 整侧失能读回。
六关节核对采用对齐终点容差，夹爪开口容差为 `3 mm`，失能前相隔至少
`0.2 s` 核对两次；若回位或核对失败，
不发送失能帧，锁存故障并保留使能，供现场处理。故障导致反馈丢失、
无法确认原位时也仅停流，不自动失能。

会话在对齐前保存从臂六关节可指令起点及夹爪反馈开口，回位轨迹继续使用
受限 minimum-jerk 规划，不跟随主臂。现有模拟反馈测试覆盖正常回位、
失能前六关节及夹爪偏差拦截、夹爪未能回位时禁止正常失能。
真机结果见第 18.9 节；本节不追认第 18.7 节已失能后的姿态。

### 18.9 双臂 30 秒摇操及失能前回位复测（2026-10-06）

开始时主臂仍处于实体示教、从臂已失能；同侧两台臂的 `0x261`～`0x266`
反馈共用 CAN ID，窗口内每关节同时有 enabled 与 disabled 样本。
旧版 `piper_arm_enable` 仅取每关节末帧，曾误报整侧失能；本轮改为逐关节检查
整个读回窗口。操作员关闭两侧示教、托稳机械臂后补做预检复位，左右总线
每关节约 `160` 个样本均为 disabled。右主臂 J6 起初与右从臂相差约 `60°`，
操作员调整后右侧对齐预检通过。左侧曾出现 `58` 个 CAN 错误帧／`2 s`，
随后 `10 s` 只读体检为 0；正式启动预检两侧错误帧均为 0。

两侧整侧使能读回、实体示教确认和自动对齐均通过；对齐最大位移左
`11.556°`、右 `29.243°`，夹爪对齐目标左 `0 mm`、右 `20.85 mm`。
随后双侧同步 `50 Hz` 运行满 `30 s`，主从反馈约 `200 Hz`，正常到时停流。
运行日志显示左侧夹爪目标在 `0～80 mm` 间变化，右侧也有 `0～80 mm`
目标；这证明目标流工作，不等于独立验收了两只夹爪的实际动态开口。

操作员关闭两侧实体示教并确认回位空间清空后，双侧自动回位启动。
左侧先回到本轮起点，失能前两次核对通过，六关节最大偏差 `0.054°`、
夹爪偏差 `0 mm`，随后整侧失能窗口全部样本为 disabled。
右侧规划回位最大位移 `59.913°`、时长 `22.467 s`；左侧先退出时，
管理器误把正常退出当作双侧联锁事件，向仍在 RETURNING 的右侧发送停止请求，
右侧因此停在离起点最大约 `4.624°` 处并保持使能。该处置没有直接失能右侧。
停止管理器后，右侧独立固定目标回位完成；两次只读核对六关节最大偏差均为
`0.088°`、夹爪距本轮起点 `0.10 mm`，然后才发送右侧整侧失能帧。
右侧每关节 `160` 个读回样本均为 disabled。最后双侧 `2 s` 只读复核均为
`CONFIRMED`、全部 disabled、错误帧为 0。

管理器联锁已改为只对仍处于 ARMING、WAIT_TEACH、ALIGNING 或 ACTIVE 的
另一侧发停流请求；一侧正常完成回位时不再打断另一侧 RETURNING。
该修复通过离线回归测试，尚需下一轮双侧真机测试验证两侧都能在同一管理器
会话内完成自动回位、核对与失能。

### 18.10 不限时双臂测试的启动故障（2026-10-07）

本轮准备阶段 `can_right` 曾为 DOWN；主机内核日志显示右 USB-CAN 适配器
在 `09:32:05` 断开、`09:32:06` 重新枚举，仍按序列号命名为 `can_right`，
但主机没有自动配置波特率并拉起接口。重新设为 `1 Mbit/s`、UP 后，
右侧主从臂反馈各约 `200 Hz`、身份 `CONFIRMED`，证明这次反馈缺失
与接口未恢复有关；未发现其他 ROS 控制节点或 CAN 监听进程占用接口。

双侧重新通过只读身份、姿态和整侧失能预检，错误帧为 0；整侧使能读回
也通过。操作员确认两只主臂实体示教后，对齐计划最大位移左 `17.637°`、
右 `5.534°`，夹爪对齐目标左 `26.55 mm`、右 `22.80 mm`。
对齐开始约 `0.6 s` 后，左侧锁存“从臂跟踪误差 `31.448°`，超过 `3°`”，
右侧随双侧联锁停止；本轮**没有进入不限时 ACTIVE 跟随**。该次日志
仅记录最大误差，没有记录对应关节和实测／目标角，无法从日志确认成因。
随后左侧每个 `0x261`～`0x266` 在 `2 s` 内均出现约 `80` 个 enabled
和 `80` 个 disabled 样本，说明同侧两台臂状态不一致；这也使左侧会话的
故障退出流程在读到 `j4 disabled` 时停止，未由会话发送失能帧。

操作员关闭实体示教后，两次独立只读核对显示左从臂六关节距本轮起点
最大 `0.151°`、夹爪偏差 `0 mm`；管理器退出后再次核对相同结果，
才单独发送左侧整侧失能帧，读回窗口各关节约 `160` 个样本均为 disabled。
右侧在会话内核对原位，六关节最大偏差 `0.103°`、夹爪偏差 `0.10 mm`，
随后整侧失能读回通过。最后两侧身份均为 `CONFIRMED`、全部 disabled、
错误帧为 0。对齐器现已在超差日志中记录关节号、实测角和目标角，
该诊断修改通过离线测试；左侧异常仍需在下一轮受控实验中定位。

后续左侧单独执行一次不发送运动目标的整侧使能检查：使能前 `2 s` 只读
窗口身份 `CONFIRMED`、全部 disabled、错误帧 0；只发送一次
`0x471 07 02` 后，`2 s` 读回中每关节约 `160` 个样本全部 enabled。

### 18.11 显式回位与新的释放确认（2026-10-07）

本次修改将当前实现统一为 `ACTIVE → RETURNING → WAIT_TEACH_RELEASE → STOPPING → IDLE_DISABLED`。启动请求后的门禁快照在使能前冻结，保存原始六关节与可指令目标，对齐重规划不覆盖回位目标。回位成功前拒绝释放确认；成功后新开确认窗口，确认后仍须重新采样核对起点并验证失能读回。保留原有夹爪回位与容差要求。

新增 `--return-timeout`（默认 `120 s`）和 `/teleop/{left,right}/cancel_return`；重复停止幂等，取消和失败锁存故障，不自动恢复。会话与独立对齐器共享接口写入锁，防止独立回位进程抢占 CAN。完整服务、超时、联锁和人工恢复约定见[工作流说明](TWO_CAN_TELEOP_WORKFLOW.md#returning-的服务与失败约定2026-10-07)。历史真机记录维持原样；本次改动尚待真机验收。

### 18.12 不限时双臂摇操中断与固定目标回位（2026-10-08）

本轮两侧在 `50 Hz` 下进入 ACTIVE，不设运行时限。开始后的独立 `60 s`
原始反馈采样中，左右 `0x2A5`～`0x2A7` 各收到 `12000` 帧，未见相邻反馈
跳变超过 `3°`；左侧收到 `131` 个 CAN 错误帧，右侧为 `0`。继续摇操时，
左侧错误帧间歇增长，`5 s` 滚动速率先后达到 `14.0 Hz`、`17.0 Hz`，最后
以 `20.2 Hz` 超过默认 `20.0 Hz` 门限。错误类别为协议违规与控制器问题，
左侧因此锁存故障并停止目标流；右侧当时错误帧仍为 `0`，仅因双侧联锁
停止。故障前两侧主从反馈均约 `200 Hz`。日志中的 `10.150 ms` 和
`12.213 ms` 短暂快照不同步只跳过对应目标周期并恢复，不是本次停流条件。

操作员关闭实体示教后，使用本轮冻结目标执行固定目标回位。左侧从当前姿态
回位的最大关节位移为 `80.595°`、用时 `30.223 s`；右侧为 `102.523°`、
用时 `38.446 s`。回位后相隔至少 `0.2 s` 的两次独立读回均稳定：左侧六关节
距冻结起点最大 `0.075°`、夹爪偏差约 `0 mm`；右侧最大 `0.077°`、夹爪
偏差 `0.1 mm`。两侧身份均为 `CONFIRMED`、错误帧为 `0`，从臂处于待机，
主从臂仍保持使能；本次诊断没有发送失能帧。

回位后同步进行的 `60 s` 只读体检显示，两条总线均约 `6181` 普通帧/秒，
估算最坏占用 `83%`，各有 `12` 个共享反馈 ID，错误帧和状态退化帧均为 `0`。
内核同时显示两接口均为 `UP / ERROR-ACTIVE`，`bus-off`、`error-pass`、
`bus-errors`、丢包均为 `0`。因此可以确定软件停流的直接原因是左侧间歇性
CAN 错误突发达到持续速率门限，右侧是联锁结果；静止窗口恢复为零说明它不是
持续掉线。当前证据尚不能在共享 ID 碰撞、总线负载余量不足、接线/终端电阻
或设备侧瞬态之间确定物理根因，仍需按总线完整性文档进行单臂隔离对照。

### 18.13 可选放宽门禁预设（2026-10-08）

为避免第 18.12 节中 `20.2 Hz` 的可恢复错误帧突发立即结束整轮测试，单侧会话
和双侧管理器新增 `--gate-profile relaxed`。该预设把 `5 s` 滚动错误率门限从
`20 Hz` 提高到 `50 Hz`，并适度放宽反馈新鲜度、快照同步跨度、ACTIVE 连续
不同步宽限及自动对齐/回位容差。所有预设参数仍可由原有逐项参数显式覆盖，默认
配置保持 `standard`，所以已有启动方式的行为不变。

该预设不跳过身份、使能/失能读回或实体示教确认，也不放开关节指令范围；
bus-off、error-passive、总线错误、外部控制流、反馈完全丢失和 CAN 写入锁仍按原
规则处理。完整阈值表与启动示例见[工作流说明](TWO_CAN_TELEOP_WORKFLOW.md#9-可选的放宽门禁预设)。

### 18.14 故障锁存后的显式 stop 回位（2026-10-08）

放宽预设真机复测中，右侧错误帧 `5 s` 滚动速率达到 `50.2 Hz`，右侧锁存
故障，左侧由双侧联锁锁存故障。此时 `/teleop/stop` 虽返回成功，但两侧原会话线程
已经结束，没有线程消费停止请求，因此不会进入 RETURNING。现场先结束故障管理器，
再用本轮冻结目标同步回位：左侧最大位移 `79.425°`、计划 `29.784 s`，右侧最大
位移 `100.321°`、计划 `37.620 s`。回位后两次独立只读核对稳定，左侧最大起点
偏差 `0.081°`、夹爪偏差 `0 mm`，右侧最大偏差 `0.053°`、夹爪偏差 `0.1 mm`；
两侧身份均为 `CONFIRMED`、错误帧为 `0`，保持 enabled 待机。

管理器现已修复该服务语义：已完成故障停流且保存了完整冻结起点的会话，再次收到
单侧或双侧 `stop` 时会启动新的恢复线程，重新取得对应 CAN 写锁，在同一会话数据上
执行固定目标回位。成功后进入新的 `WAIT_TEACH_RELEASE`，继续要求实体示教释放确认、
原位核对和失能读回；该路径不能重新进入 ACTIVE。故障停流尚未结束、冻结起点缺失、
写锁被占用或故障条件仍存在时会明确拒绝或再次锁存，不再虚报“已请求回位”。
