# 受控使能测试操作手册

本手册描述如何把一台 Piper 从臂从已验证的 **失能** 状态带到 **使能** 状态，
全程不下发任何运动指令，并在事后加以证明。手册刻意拆成「只读通电前检查」
和「唯一一次通电动作」两段，避免两者被混淆。

本仓库中没有任何逻辑会自动使能机械臂。`auto_enable` 始终为 `false`；
使能永远是一个显式的、有人在场的动作。

> **要做关节空间运动测试的话，先读「关节空间指令的范围陷阱」一节。** 那里有两个会
> 让测试**静默失败**的陷阱（含越界目标的指令行为未定义、速度字段会变成 100%），
> 以及一个**必需**的前置步骤「使能后必须先归位」——跳过它，第一条指令会什么都不做
> 或产生附带位移，且不会报错。

## 门禁：以下条件全部成立前不要开始

| # | 前置条件 | 确认方式 |
| --- | --- | --- |
| 1 | 机械臂工作空间内无人，且急停可达 | 人工确认 |
| 2 | 机械臂处于空载状态，或负载已固定足以抵抗小幅沉降 | 人工确认 |
| 3 | 机械臂在当前姿态下已有支撑，关节变硬后不会失稳 | 人工确认 |
| 4 | 两臂均报 `DISABLED`，且六个关节的反馈都是新鲜的 | `piper_enable_check --expect disabled` |
| 5 | 四路 CAN 均为 `ERROR-ACTIVE`，无总线错误 | `ip -details -statistics link show dev can_fl can_fr` |
| 6 | 没有控制节点在发布运动，且 `/pos_cmd_*`、`/joint_ctrl_cmd_*` 都没有发布者 | `ros2 topic info /pos_cmd_left` 显示 `Publisher count: 0` |

使能关节会让它进入力矩保持状态、锁住当前位置。它不应产生位移，但轻微的
沉降动作是正常的；而承担重力的关节变硬时会顶住而不会下垂。这就是第 3 条
重要的原因。

## 第 1 步 —— 只读通电前检查（不改变任何状态）

按检测阶段完全相同的方式拉起接口和从臂节点。此步骤每个接口只发送 13 帧
启动查询（`0x472` 共 12 帧、`0x4AF` 共 1 帧）；实测节点此后空闲期间的发送
增量为零。

```bash
cd /home/mips/piper_ros
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select piper_msgs piper
source install/setup.bash

ros2 launch piper start_two_piper.launch.py \
  auto_enable:=false \
  gripper_exist:=false
```

在第二个终端里取一份不依赖节点的基线。该工具自行解码驱动器的原始反馈帧，
以接收-only 方式打开套接字，并已验证不发送任何帧：

```bash
# 基线：两臂必须报 DISABLED，且退出码为 0。
ros2 run piper piper_enable_check --port can_fl --port can_fr \
  --duration 3 --timeout 0.5 --expect disabled
```

记录发送计数器，以便后续把通电动作的流量归属清楚：

```bash
for i in can_fl can_fr; do echo "$i tx=$(cat /sys/class/net/$i/statistics/tx_packets)"; done
```

## 第 2 步 —— 只使能左臂

只使能一条臂，不要同时使能两条，这样一条臂出现意外时不会和另一条叠加。
左臂是 `can_fl`。

```bash
# 使能：这是本手册中第一条也是唯一一条改变状态的命令。
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: true}"
```

预期：节点观察到六个关节全部使能后，`/enable_srv_left` 返回
`enable_response: true`。若返回 `enable_response: false`，表示节点等待
「六分之六」超时。

## 第 3 步 —— 独立确认使能结果

```bash
# 预期 ENABLED，且六个关节都新鲜。
ros2 run piper piper_enable_check --port can_fl --timeout 0.5 --expect enabled

# 预期 state 为 ENABLED、all_enabled 为 True、can_port 为 can_fl。
ros2 topic echo /arm_enable_status_left --once

# err_code 必须保持为 0。
ros2 topic echo /arm_status_left --once
```

成功要求**独立原始帧工具**与**节点话题**两者一致给出 `ENABLED`。若两者不
一致，立即停止，并在证伪之前一直把该臂当作已使能处理，然后将其失能。

### `ctrl_mode` 不能佐证使能位

2026-09-23 实测：使能成功后，左臂和右臂的 `ctrl_mode` 都仍为 `0`（STANDBY）。
`driver_enable_status` 与 `ctrl_mode` 描述的是两件不同的事——前者说明驱动器
已通电并保持位置，后者说明机械臂已切换到接受运动指令的模式。单纯的使能不会
切换模式，因为尚未下发 `MotionCtrl_2`。因此使能后 `ctrl_mode` 为 `0` 是预期
行为而非故障，且 `ctrl_mode` 不可用作「机械臂是否已通电」的证据。

关节确实保持了位置：在实测的使能/失能周期内，左臂六个关节的最大偏差为
0.000000000 rad，因此「关节变硬但没有移动」是本场景下的正常结果。

## 第 4 步 —— 失能并验证

```bash
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: false}"
ros2 run piper piper_enable_check --port can_fl --expect disabled
```

## 回滚

将机械臂失能，并确认其处于非使能状态：

```bash
ros2 service call /enable_srv_left piper_msgs/srv/Enable "{enable_request: false}"
ros2 run piper piper_enable_check --port can_fl --expect disabled
```

响应字段是按请求命名的，而不是按结果状态命名的：调用**失能**同样会返回
`enable_response: true`，它表示请求的操作已完成，**并不**表示机械臂已使能。
要判断机械臂是否带电，请读 `piper_enable_check` 的结果，而不是读响应字段。

若服务无响应，停止节点（`Ctrl-C`）并对机械臂断电重启。节点退出并不会让
机械臂失能，因此在认定机械臂已松懈之前，务必先用 `piper_enable_check` 验证。

## 总线上实际发生了什么

以下为实测发送增量，它界定了本手册能做到的范围：

| 事件 | 每接口帧数 |
| --- | --- |
| 节点启动（`PiperInit`） | +13（`0x472` 查询 12 帧、`0x4AF` 1 帧） |
| 节点空闲且 `auto_enable:=false` | 每 15 秒 +0 |
| `piper_enable_check` | +0 |
| 左臂一次使能加一次失能 | `can_fl` +8，`can_fr` +0 |

使能/失能流量被限制在 `can_fl` 上，因此右臂所在总线根本没有看到任何使能帧。
使能路径是节点既有行为，它在每次迭代中下发 `EnableArm(7)` 以及一条夹爪使能
指令，直到六个关节全部报使能为止，这就是帧数不是 1 的原因。

`EnableArm(7)` 覆盖 7 号电机即夹爪，而 `handle_enable_service` 中的
`GripperCtrl` 调用不受 `gripper_exist` 保护。因此即使传入
`gripper_exist:=false`，使能机械臂的同时也会激活夹爪并把它驱向位置 0。在被测
的左臂上夹爪原始角度为 `-500`（约 -0.5 mm，实际上已处于其闭合零点），所以这
是一次亚毫米级位移；但它确实是一条真实的夹爪指令，属于前置条件的一部分——
**手指之间不能有任何东西**。

## `piper_enable_check` 的退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 每条臂都符合 `--expect`，且所有关节都新鲜 |
| 1 | 出现部分使能，或判定结果与 `--expect` 不符 |
| 2 | 使能状态不完整：有关节缺失或陈旧 |
| 3 | 初始化失败，例如接口无法打开 |

退出码 1 和 2 是与安全相关的两个。`PARTIAL` 表示六个关节中只有部分使能，
此时绝不能把机械臂当作已使能处理。`UNKNOWN` 表示某个关节的反馈缺失或已旧于
`--timeout`，因此不再采信它最后一次上报的使能位。

## 运动门禁

运动是以**实时读数**为门禁，而不是以锁存的使能标志为门禁。`pos_callback` 与
`joint_callback` 只在 `GetEnableFlag()` 为真**且**该时刻六个关节全部使能时才
转发指令。使能服务只在使能那一刻确认过一次「六分之六」；若不做实时复检，此后
掉线的关节仍会放行运动。

门禁只可能拒绝运动，不可能产生运动，因此它自身出故障时是失败在安全方向。当它
因为「标志位说已使能、但六轴并不同意」而拒绝时，会记录一次
`motion refused, the six joints are not all enabled (<六轴明细>)`，按阻断片段
记录而非每个回调都刷屏。

该门禁尚未在硬件上实测过拒绝路径，因为要触发它必须向已使能的机械臂发布一条
运动指令。其逻辑由覆盖六轴全部状态的单元测试保障；真机路径将在运动测试开始时
首次被走到。

## 关节空间指令的范围陷阱（2026-09-23 首次运动测试实测）

**反馈角度不一定能当作指令角度使用。** 这是第一次发送运动指令时踩到的坑，务必
先读这一节。

关节位置指令（`JointCtrl`，CAN `0x155`/`0x156`/`0x157`）对每个关节有可指令范围，
单位度：

| 关节 | 可指令范围 | 关节 | 可指令范围 |
| --- | --- | --- | --- |
| joint1 | [−150, 150] | joint4 | [−100, 100] |
| joint2 | **[0, 180]** | joint5 | [−70, 70] |
| joint3 | **[−170, 0]** | joint6 | [−120, 120] |

越界的目标值**不会被驱动器拒绝，而是被钳制到最近的边界**。后果是：当你只想让
joint1 动、于是把其余关节的目标设成它们当前角度以求「保持不动」时，只要某个关节
的当前角度已经越界，它就会被钳到边界，**「保持不动」变成一次真实的运动**。

实测经过：命令 joint1 +0.5°（实际移动 +0.4658°），但 joint2 从 −2.294° 被钳到 0
（移动 2.38°），joint3 从 +1.477° 被钳到 0（移动 1.57°）。二者都是承重关节，在
失能状态下受重力下垂，其自然停位恰好落在各自范围之外——**只要在这个姿态下发任何
关节空间指令，这两次位移就必然发生**。

因此运动测试前必须做两件事：

1. **用 `piper_joint_move` 而不是自己拼 `joint_ctrl_cmd`**。它在发送前校验全部
   六个关节的目标值，发现越界即拒绝发送并列出预计的非预期位移；确实知情并接受时
   才加 `--allow-clamped`。
2. **先把机械臂摆到所有关节都在范围内的姿态**。若承重关节因重力停在范围外，先在
   有人看护的前提下把它托到范围内，再进入运动测试。

```bash
# 干跑：读取当前姿态、校验范围、打印将要发送的内容，不发送任何东西
ros2 run piper piper_joint_move --target joint1 --delta-deg 0.5

# 确认无误后执行；加上 --send 才真正发布
ros2 run piper piper_joint_move --target joint1 --delta-deg 0.5 --send
```

### 失能下坠会必然造成对齐位移

承重关节（joint2、joint3）在**失能状态下无法停在软件零位**：重力会把它们压到机械
限位上，而机械限位在软件限位之外。实测四台臂全部如此，静置位置高度一致：

| 接口 | joint2 静置 | joint3 静置 |
| --- | --- | --- |
| `can_ml` | −2.044° | +2.120° |
| `can_mr` | −1.848° | +2.010° |
| `can_fl` | −2.597° | +1.810° |
| `can_fr` | −1.956° | +1.727° |

所以「使能前先把臂摆进范围」解决不了问题——一失能它又会掉回去，下次使能照旧越界。
**每次失能-使能循环都会带来一次对齐位移**，这是该机械臂的设计特征，不是故障。

### 放宽软件限位可以减小对齐位移（2026-09-23 已实施并验证）

`MotorAngleLimitMaxSpdSet`（CAN `0x474`）可直接改写驱动 flash 里的限位，无需使能：

```python
piper.MotorAngleLimitMaxSpdSet(2, 1800, -20, 300)   # joint2 下限 0    -> -2.0°
piper.MotorAngleLimitMaxSpdSet(3, 12, -1700, 300)   # joint3 上限 0    -> +1.2°
```

（joint3 的 +1.2° 当天稍后又放宽到 **+2.0°**，见下文「已推广到全部四台臂」。）

**三个字段必须全部显式给值。** 不能用默认的 `0x7FFF`（"不修改"）——该语义是固件
V1.5-2 之后才支持的，在旧固件上 `max_joint_spd` 的 `0x7FFF` 会被解释成
32767×0.001 = 32.767 rad/s，远超合法上限 3000。

实施要点：

- **软件限位不能越过机械限位**，否则指向不可达位置的指令会让关节顶死、堵转、过热。
  放宽后的边界要在机械限位内侧留 0.2~0.4° 裕度，别贴着机械限位设。
- 写入后**立即生效，不需要重启**：读回 `0x473` 就是新值（这一点与 SDK 脚本注释
  「不可实时更新」的印象相反，实测无需重启）。
- 写入不使能、不发运动指令，全程可保持失能。
- 改完**必须同步 `piper_feedback.py` 里的 `JOINT_COMMAND_LIMITS_DEG`**，否则工具
  预告的越界量会算错。
- 回滚：`MotorAngleLimitMaxSpdSet(2, 1800, 0, 300)` 与
  `MotorAngleLimitMaxSpdSet(3, 0, -1700, 300)`。

**实测效果**（`can_fl`，`joint1 +0.5° @ 2%`，判决点看 joint2 停在哪）：

| 关节 | 发送前 | 发送后 | 实际位移 | 放宽限位前会是 |
| --- | --- | --- | --- | --- |
| joint1 | −0.550° | −0.079° | +0.471° | 同（按指令） |
| joint2 | −2.597° | **−2.058°** | **+0.539°** | +2.597° |
| joint3 | +1.810° | **+1.080°** | −0.730° | −1.810° |

joint2 停在 −2.058° 而**不是 0°**，这是限位改动确实作用于控制行为的判决性证据。
附带位移从 2.597°/+1.810° 降到 0.539°/+0.730°。两处停位都略越过目标
0.06~0.12°，那是重力负载下的伺服静差，不是限位失效。

注意 joint3 的 +1.2° 上限**偏窄**：四台臂的 joint3 静置位置在 +1.727~+2.120°，都
高于它，所以 joint3 侧仍有约 0.5~0.9° 的对齐位移。因此当天又把它放宽到 **+2.0°**，
静置最高的那台（+2.120°）残差随之降到 0.120°，其余更小。再往上（约 +2.4°）需要先
确认机械限位的真实值；当前取值是权衡后**有意的选择**：宁可保留这零点几度的对齐位移，
也不把软件限位贴到机械限位上。

**2026-09-23 已推广到全部四台臂，joint3 上限当天两次放宽：0 → +1.2° → +2.0°。**
四台臂读出厂限位完全一致，均为 `j2[0,180]`、`j3[-170,0]`，因此统一写入 `j2` 下限
−2.0°、`j3` 上限 +2.0°。逐台读回确认四臂限位现在完全相同：

| 接口 | j1 | j2 | j3 | j4 | j5 | j6 |
| --- | --- | --- | --- | --- | --- | --- |
| `can_ml` | [−150, 150] | **[−2.0, 180]** | **[−170, 2.0]** | [−100, 100] | [−70, 70] | [−180, 180] |
| `can_mr` | [−150, 150] | **[−2.0, 180]** | **[−170, 2.0]** | [−100, 100] | [−70, 70] | [−180, 180] |
| `can_fl` | [−150, 150] | **[−2.0, 180]** | **[−170, 2.0]** | [−100, 100] | [−70, 70] | [−180, 180] |
| `can_fr` | [−150, 150] | **[−2.0, 180]** | **[−170, 2.0]** | [−100, 100] | [−70, 70] | [−180, 180] |

各台 `max_joint_spd` 均为 300（0.3 rad/s ≈ 17.2 deg/s），至今未被改动。**2026-09-23
曾计划把它放大到 1500（≈86 deg/s）以提升遥操作跟随能力，当天真机实测后判定不需要**：
压住跟随速度的是遥操作自己的 `--speed` 默认值（10% × 3 rad/s ≈ 17.2 deg/s，与 300 的
换算值恰好相同），把它改为 100% 后 follower 的持续速度就达到了 86 deg/s，而
`max_joint_spd` 全程保持 300。详见 `docs/PIPER_TELEOP.md` 的「跟随速度」一节；改写该
字段的工具（`piper_speed_limit`）、失能前置条件与逐台回滚命令在紧随其后的一节里备用。

写入时**必须用该台臂自己读到的原值填充未修改的字段**，不能照抄另一台臂的值——
否则会把本来不同的限位覆盖掉。四台臂恰好出厂一致只是这次的运气。

**逐台回滚命令**（把 j2/j3 恢复为出厂值，其余关节本来就没动）：

```python
piper.MotorAngleLimitMaxSpdSet(2, 1800, 0, 300)
piper.MotorAngleLimitMaxSpdSet(3, 0, -1700, 300)
```

对每台要回滚的臂，用该臂的 CAN 口各执行一次这两条。注意这两条会把 joint3 上限一起
退回出厂值 0°，连当天放宽的部分也一起回滚——只想退回限速、保留放宽后的角度限位时，
用 `piper_speed_limit`（它只改 `max_joint_spd`，角度限位取写入那一刻读回的值）。

### 含越界目标的指令行为未定义（2026-09-23 实测）

**不要把「发送越界目标」当作可依赖的行为。** 实测两台**固件版本完全相同**
（`S-V1.8-2`）、**限位完全相同**的从臂，在同一场景下行为相反：

| 臂 | 越界关节 | 结果 |
| --- | --- | --- |
| `can_fl`（左） | joint2 低于下限、joint3 高于上限 | **执行并钳制**，附带位移 0.539° / 0.730° |
| `can_fr`（右） | joint3 高于上限 | **整条指令被拒**，全关节零位移（含原本合法的 joint1） |

右臂的拒绝行为用五个实验隔离确认（都是 joint1 ±0.5° @ 2%，只改变 joint3 目标是否越界）：

| 实验 | joint3 目标 | joint1 结果 | joint3 结果 |
| --- | --- | --- | --- |
| A | 越界 +1.726° | **0.0000°** | 0.0000° |
| B | 范围内 +1.026° | — | **−0.632°** 已执行 |
| C | 范围内 | **+0.4688°** 已执行 | 0.0000° |
| D | 越界 +1.594° | 0.0000° | −0.038°（反向静差，未执行） |
| E | 范围内 | **−0.4688°** 已执行 | 0.0000° |

判定「被拒」的依据不是「没动」本身，而是：回调已触发、门禁通过、`ctrl_mode` 已切到
`CAN_CTRL`、总线上恰好发出 4 帧、`err_code=0`，但驱动器**电流仅 1**（根本没尝试出力），
且 `motion_status` 停在 `REACH_TARGET_POS_SUCCESSFULLY`——即它认为目标就是当前位置。

**而只要所有目标都在限位内，行为就是精确且可重复的**：实验 C 与 E 的双向验证中，
joint1 位移为 +0.4688° 与 −0.4688°（命令 ±0.5°，误差 6%），**其余五个关节位移全部为
0.0000°**。这是做单关节测试时应追求的状态。

### 使能后必须先归位（必需步骤，不是可选）

承重关节在失能时必然下坠到限位外，所以**每次使能后的第一条关节指令都含越界目标**。
在那条指令被拒（右臂）或被钳制（左臂）之前，任何测试都不会按预期进行。这就是右臂
首次测试「指令发出、链路完好、却什么都不动」的原因。

归位必须**一次把所有越界关节都带进限位内**。只归一个关节是不够的——其余越界关节
仍会让整条指令失效。实测中 joint2 仅越界 0.076° 就足以让一条「归位 joint3」的指令
被拒绝。用 `--normalize` 一次完成：

```bash
# 干跑：列出哪些关节越界、会被带到哪里，不发送任何东西
ros2 run piper piper_joint_move --side right --normalize

# 确认无误后执行
ros2 run piper piper_joint_move --side right --normalize --send
```

`--normalize` 把每个越界关节放到距限位边界 0.2° 的内侧（留出伺服静差的余量），
其余关节保持当前值。因为所有目标都合法，工具不会拒绝，**因此不需要 `--allow-clamped`**；
反过来说，如果某条归位指令需要加 `--allow-clamped` 才发得出去，说明还有关节没归到位。

归位后复查，应显示六个关节全部「在范围内」：

```bash
ros2 run piper piper_joint_move --side right --target joint1 --delta-deg 0.5
```

归位后关节停在限位内，但**下一次失能仍会重新下坠**，所以每个使能-测试会话都要重做
一次。想彻底免除这一步，只能继续放宽软件限位（见上一节的权衡）。

### 另一个坑：速度字段

`velocity` 字段决定速度。节点的逻辑是：`velocity` 全零或为空时调用
`MotionCtrl_2(0x01, 0x01, 100)`，即 **100% 速度**；只有恰好 7 个元素时才会用第 7
项作为速度百分比。所以**要低速就必须给 7 个元素且第 7 项非零**，`piper_joint_move`
已经这样构造。

### 指令帧数

一条关节空间指令在总线上恰好产生 **4 帧**：`MotionCtrl_2`（`0x151`）1 帧，加上
`JointCtrl` 的 `0x155`/`0x156`/`0x157` 各 1 帧。可用它核对指令是否只发了一条。

## 为什么新鲜度检查放在这里而不放在话题里

`/arm_enable_status_*` 在某个关节的反馈帧被收到过之后就把该关节标为有效，这
足以区分「从未上报」与「上报为失能」，但它不限制该帧有多旧。`piper_enable_check`
补上了这个上限，因此一个在上报过之后转为静默的关节无法继续贡献一个陈旧的使能
位。正因如此，通电前检查与使能后检查的权威判据是该工具。
